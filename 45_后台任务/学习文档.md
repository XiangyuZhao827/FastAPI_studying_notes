# 04｜后台任务（Background Tasks）

**FastAPI 用户指南 · 独立复习手册｜核心问题：什么时候可以先向客户端返回，再执行后续操作？**

官方文档：https://fastapi.tiangolo.com/zh/tutorial/background-tasks/

## 一、本章主要学习什么？

假设用户调用 Agent 接口，希望尽快得到“文件已收到”的回应。服务器已经完成权限检查、文件保存等必要操作，还打算写一条**非关键的通知记录**。这条记录不影响本次请求是否成功，那么用户没有必要一直等待它。

`BackgroundTasks` 用于登记响应发送完成后执行的任务。它是处理**请求后的附带工作**的一种轻量工具，而不是重新设计整个 Agent 推理流程。

对比两种时序：

```text
没有后台任务：请求 → 必要工作 → 附带操作 → 返回响应
有后台任务：请求 → 必要工作并登记附带操作 → 发送响应 → 执行附带操作
```

**最关键的认知：**“任务已登记”不等于“任务已完成”，HTTP 响应成功也不保证后续附带任务一定成功。

## 二、官方的最小示例

官方以模拟“发送通知”为例，实际上只是写入本地文件，并没有连接邮件服务。

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()


def write_notification(email: str, message=""):
    with open("log.txt", mode="w") as email_file:
        content = f"notification for {email}: {message}"
        email_file.write(content)


@app.post("/send-notification/{email}")
async def send_notification(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(
        write_notification,
        email,
        message="some notification",
    )
    return {"message": "Notification sent in the background"}
```

在本章里，读懂三个位置即可：

| 部分 | 作用 | 小白理解 |
| --- | --- | --- |
| `background_tasks: BackgroundTasks` | FastAPI 提供任务登记对象 | 有一个登记待办的清单 |
| `.add_task(write_notification, email, ...)` | 登记函数和参数 | 指定以后要做什么 |
| `return {...}` | 给客户端当前请求的回应 | 回应发送后，后台任务才运行 |

`add_task()` 要传入函数本身，不是 `write_notification()` 的提前调用结果。后台任务函数既可以用普通 `def`，也可以用 `async def`；是否异步不改变任务的执行时机。

## 三、如何与 Depends 配合？

你以前在依赖项章节见过：一个依赖可以先读取 Query、Header，再交给路由函数。官方进一步说明，依赖函数本身也可以接收 `BackgroundTasks`，并向同一次请求登记任务。

```python
from fastapi import BackgroundTasks


def write_log(message: str):
    with open("log.txt", mode="a") as log:
        log.write(message)


def get_query(background_tasks: BackgroundTasks, q: str | None = None):
    if q:
        background_tasks.add_task(write_log, f"found query: {q}\n")
    return q
```

这个示例保留了官方依赖中的主要思路：依赖负责读取查询参数 `q`，必要时登记日志工作。实际使用还需要将它通过 `Depends(get_query)` 连接到路由。FastAPI 会汇总同一次请求及其依赖关系中登记的后台任务。

**区别：**`Depends()` 负责依赖求解；`BackgroundTasks` 负责登记响应后的操作。两者可以同时存在，不是替代关系。

## 四、Agent 实战：应该怎样使用？

### 场景 A：对话完成后的非关键统计

Agent 已经生成回答，应用还要写简单计数日志或辅助通知。若这些信息允许延后处理、即使失败也不会丢失核心用户数据，可以考虑使用 `BackgroundTasks`。

### 场景 B：文档已被接收后的轻量收尾

用户上传文件，后台已经验证权限、限制大小，并安全保存原文件。对于短小、无关键可靠性要求的整理动作，可以考虑在响应后处理。

但如果后续是“扫描几百页 PDF、嵌入向量、长期运行的 LangGraph 工作流”，仅用 `BackgroundTasks` 并不稳妥：它没有自动提供任务持久化、跨进程 Worker、失败重试、断点恢复等机制。

### 场景 C：研究任务状态通知

如果业务处理是几分钟甚至几小时的任务，典型设计是先返回 `202 Accepted` 和任务 ID，使用专门的任务处理与状态存储机制持续运行，再用查询接口或 SSE 查看进度。这里不应把 `BackgroundTasks` 当作完整可靠任务系统。

| 工作类型 | 是否适合直接使用 BackgroundTasks | 为什么 |
| --- | --- | --- |
| 简单日志、通知 | 可以考虑 | 请求无须等待、工作轻量 |
| 简单非关键收尾 | 可以考虑 | 对可靠性要求低 |
| 大型 RAG 向量化 | 通常不建议独立依赖它 | 耗时、重要、可能需要重试 |
| 多步长时间 Agent 任务 | 通常不建议独立依赖它 | 需要持久任务状态与调度 |

## 五、与 SSE、流式响应的关系

SSE 在**响应过程中**持续向客户端传送事件；`BackgroundTasks` 在**响应结束后**运行后续工作。不要把登记到同一个 SSE 响应上的后台任务误以为会在事件流仍持续发送时就开始执行。它们解决的是两个不同问题。

如果用户需要实时看见长任务进度，不是简单地把 `BackgroundTasks` 和 SSE 写在一起就可以：还需要真实的任务执行状态、能持续查询或订阅的状态来源。

## 六、常见误区

1. **后台任务＝独立进程？** 不是。FastAPI 的 `BackgroundTasks` 通常与当前应用响应处理机制绑定。
2. **响应 200/202＝后续任务完成？** 不是，只表示当前 HTTP 响应成功。真正的完成情况要另行管理。
3. **文件已经上传＝文件已经处理完成？** 不一定，应区分“已接收”“处理中”“已完成”。
4. **`add_task()` 里写 `write_notification()`？** 不推荐，这会提前调用函数；应传 `write_notification` 本身。
5. **后台任务就是 Celery 等任务队列？** 不是。复杂任务队列通常支持独立 Worker、重试和持久存储。

## 七、5 道复习题（附答案解析）

**1. BackgroundTasks 的执行时机通常是什么？**  答：响应发送完成后；因此它适合无须阻塞当前响应的附带工作。

**2. 使用 `background_tasks.add_task(send, email)` 是立刻调用 send 吗？**  答：不是。这行主要登记要执行的函数及其参数。

**3. 长时间的研究型 Agent 任务一定适合 BackgroundTasks 吗？**  答：不是。可靠性、持久化、恢复与重试要求较高时应考虑任务队列。

**4. 如果用户只收到“已接收”，能否认定后台文件处理成功？**  答：不能。要设计状态查询或其他结果反馈。

**5. 为什么不能通过同一个未结束的 SSE 响应上的 BackgroundTasks 实时推送进度？**  答：后台任务在该响应结束后才运行，不能替代流式过程中的业务执行。

## 八、思考题

用户上传一份研究报告，服务器要保存文件、解析文本、制作向量索引，并在网页显示进度。哪些是响应前的必要检查？哪些工作可后台化？怎样让用户知道是否真的完成？

**参考方向：**先认证授权、验证上传并持久保存，再登记可靠任务并返回任务 ID；解析与向量化由专门工作执行器处理、维护状态；通过状态查询或 SSE 推送进度。轻量非关键通知可以考虑 `BackgroundTasks`。

**本章一句话总结：**BackgroundTasks 让非关键附带工作在响应后执行，但不自动提供可靠的长任务调度与状态恢复。
