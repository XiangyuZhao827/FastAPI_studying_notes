# 第一章：响应模型－返回类型

## 一、为什么 FastAPI 需要响应模型？

你已经很熟悉下面的代码了：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class ChatRequest(BaseModel):
    message: str


@app.post("/chat")
def chat(request: ChatRequest):
    return {
        "answer": f"Agent 收到了：{request.message}"
    }
```

这个接口能正常运行。

用户发送：

```json
{
  "message": "请解释 FastAPI"
}
```

服务器返回：

```json
{
  "answer": "Agent 收到了：请解释 FastAPI"
}
```

但这里存在一个问题：

**FastAPI 只知道用户发送的数据应该符合 `ChatRequest`，我们却没有明确规定响应应该是什么结构。**

假设以后你的业务函数写错了：

```python
return {
    "anser": "你好"
}
```

这里误把 `answer` 写成了 `anser`。

如果没有响应模型，这个字典仍然可能被正常序列化并返回。

但前端可能正准备读取：

```javascript
result.answer
```

于是出现前后端数据格式不一致的问题。

因此，我们希望明确声明：

> 我的 `/chat` 接口必须返回一个包含 `answer` 字段的数据对象，而且 answer 必须是字符串。

这就需要响应模型。

## 二、官网第一种写法：使用返回类型注解

先看官方教程的核心示例。

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    description: str | None = None
    price: float
    tax: float | None = None
    tags: list[str] = []


@app.post("/items/")
async def create_item(item: Item) -> Item:
    return item
```

这一次我们重点看：

```python
async def create_item(item: Item) -> Item:
```

为什么这里出现了两个 `Item`？

### 1. 第一个 Item

```python
item: Item
```

它是**函数参数的类型注解**。

告诉 FastAPI：

> 客户端发送的 JSON 请求体应该符合 Item 模型。

例如：

```json
{
  "name": "Book",
  "price": 50
}
```

FastAPI 会使用 Pydantic 验证它，然后创建 `Item` 对象。

### 2. 第二个 Item

```python
-> Item
```

这是 Python 的**函数返回类型注解**。

它表示：

> 这个函数预期返回 Item 类型的数据。

以前你学过：

```python
def add(a: int, b: int) -> int:
    return a + b
```

这里的：

```python
-> int
```

就表示函数返回整数。

现在：

```python
def create_item(item: Item) -> Item:
```

表示函数预期返回一个 `Item`。

但有一个重要区别：

**普通 Python 的返回类型注解本身不会强制进行运行时验证，而 FastAPI 会读取有效的返回类型注解，用它建立响应模型，从而校验、序列化和过滤 HTTP 响应。**

### 3. 换成 Agent 代码

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class ChatRequest(BaseModel):
    message: str


class ChatResponse(BaseModel):
    answer: str


@app.post("/chat")
def chat(request: ChatRequest) -> ChatResponse:

    result = ChatResponse(
        answer=f"Agent 收到了：{request.message}"
    )

    return result
```

请注意：

```python
request: ChatRequest
```

表示**输入模型**。

```python
-> ChatResponse
```

表示**输出模型**。

它们负责不同的事情，不要求相同。

### 4. 这时 `/docs` 有什么变化？

打开：

```text
http://127.0.0.1:8000/docs
```

你会发现接口文档不仅说明请求体应该包含 `message`，还会描述正常响应中应该包含 `answer`。

这就是 FastAPI 根据输入和输出模型自动生成 OpenAPI 文档的作用。

## 三、官网第二种写法：`response_model=...` ⭐

这一种是我建议你在 Agent API 项目中优先掌握的写法。

```python
@app.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest):
    return {
        "answer": f"Agent 收到了：{request.message}"
    }
```

关键是：

```python
response_model=ChatResponse
```

它写在：

```python
@app.post(...)
```

**路径操作装饰器中**。

这与你之前学习的 `Body()`、`Query()`、`Cookie()`、`Header()` 不一样。

| 工具 | 写在哪里？ |
|---|---|
| `Query()` | 函数参数声明 |
| `Body()` | 函数参数声明 |
| `Cookie()` | 函数参数声明 |
| `Header()` | 函数参数声明 |
| `response_model=...` | 路由装饰器 |

### 1. 它与 `-> ChatResponse` 有什么区别？

下面这两段代码都可以声明响应结构。

**方式 A：返回类型**

```python
@app.post("/chat")
def chat(request: ChatRequest) -> ChatResponse:
    return ChatResponse(
        answer="你好"
    )
```

**方式 B：response_model**

```python
@app.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest):
    return {
        "answer": "你好"
    }
```

重要区别在于，方式 B 允许你的函数直接返回一个 Python 字典，而不必把函数的返回类型标注成 `ChatResponse`。

在真实项目中，业务函数可能返回：

- Python 字典；
- Pydantic 模型；
- 某些数据库对象；
- Agent 执行器产生的数据结构。

你希望它们最终都按照统一的响应模型输出，就可以通过：

```python
response_model=ChatResponse
```

完成响应校验和序列化。

如果同时写了返回类型和 `response_model`，FastAPI 使用 **`response_model` 作为响应模型声明的优先依据**。

## 四、response_model 最重要的四个功能

这是本章的必考知识。

### 功能 1：验证响应数据

例如模型：

```python
class ChatResponse(BaseModel):
    answer: str
    agent_id: int
```

我们要求返回：

```json
{
  "answer": "你好",
  "agent_id": 2
}
```

如果你的函数返回：

```python
return {
    "answer": "你好"
}
```

缺少必填的：

```python
agent_id
```

那么输出没有符合 `ChatResponse` 的要求。

这属于**服务器代码的错误**，而不是用户传入的参数错误。

因此，在常见默认配置下，FastAPI 会产生响应验证错误并返回：

**HTTP 500 Internal Server Error。**

这点与之前的 422 有非常重要的区别。

### 功能 2：自动生成响应文档

Swagger UI 可以知道服务器的正常响应应该是什么结构。

前端开发者就可以据此编写：

```javascript
result.answer
result.agent_id
```

而不用完全依赖猜测。

### 功能 3：序列化响应数据

例如 Python 对象：

```python
ChatResponse(
    answer="你好",
    agent_id=2
)
```

最终会被转换成符合响应模型约定的 JSON：

```json
{
  "answer": "你好",
  "agent_id": 2
}
```

### 功能 4：过滤不应该对外返回的字段 ⭐⭐⭐

这是非常重要的安全功能。

假设 Agent 内部返回：

```python
return {
    "answer": "你好",
    "agent_id": 2,
    "internal_prompt": "内部系统提示词",
    "debug_notes": "内部调试信息"
}
```

但响应模型只定义：

```python
class ChatResponse(BaseModel):
    answer: str
    agent_id: int
```

接口写成：

```python
@app.post("/chat", response_model=ChatResponse)
```

那么正常响应中，未在响应模型中定义的额外字段会被过滤掉。

客户端收到：

```json
{
  "answer": "你好",
  "agent_id": 2
}
```

不会收到：

```json
{
  "internal_prompt": "...",
  "debug_notes": "..."
}
```

**response_model 不只是格式检查，也可以帮助你限制对外输出的字段。**

不过，实际项目依然应该主动避免把密钥、原始凭据和敏感内部信息放入不必要的数据结构中。响应过滤是重要保护，但不是整个系统唯一的安全措施。

## 五、重点对比：输入错误 422 vs 输出错误 500

假设代码是：

```python
from pydantic import BaseModel, Field


class ChatRequest(BaseModel):
    message: str = Field(min_length=1)


class ChatResponse(BaseModel):
    answer: str


@app.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest):
    return {
        "answer": request.message
    }
```

我们比较两种不同的错误。

### 情况 A：用户发送错误请求

```json
{
  "message": ""
}
```

因为：

```python
Field(min_length=1)
```

不允许空字符串。

因此请求在输入校验阶段失败：

```text
客户端请求
    ↓
ChatRequest 校验失败
    ↓
HTTP 422
```

业务函数通常不会执行。

### 情况 B：用户请求完全合法，但后端返回了错误数据

请求：

```json
{
  "message": "你好"
}
```

假设函数错误地返回：

```python
return {
    "reply": "你好"
}
```

但响应模型规定：

```python
class ChatResponse(BaseModel):
    answer: str
```

这里缺少 answer。

执行流程：

```text
客户端请求
    ↓
ChatRequest 校验成功
    ↓
执行 chat 函数
    ↓
返回错误结构
    ↓
ChatResponse 校验失败
    ↓
HTTP 500
```

这里服务器认为是自己的程序没有正确返回数据，因此不能把责任归结为客户端输入错误。

| 对比 | 请求模型验证失败 | 响应模型验证失败 |
|---|---|---|
| 主要发生在 | 执行业务函数之前 | 业务函数返回数据之后 |
| 谁的数据有问题 | 客户端请求数据 | 服务端返回数据 |
| 常见状态码 | **422** | **500** |
| 典型例子 | 缺少 message | 返回数据缺少 answer |
| 谁应该修改 | 调用方或前端 | 后端开发者 |

这一点一定要掌握，以后调试 Agent API 会非常有用。

## 六、`response_model_exclude_unset=True` 是什么？

这是官方教程中很容易与 `Field(default=...)` 混淆的知识。

假设你有一个任务模型：

```python
class TaskResponse(BaseModel):
    task_id: int
    status: str = "pending"
    answer: str | None = None
    tags: list[str] = Field(default_factory=list)
```

现在某个任务还没有产生答案。

后端只返回：

```python
return {
    "task_id": 101
}
```

如果接口声明：

```python
@app.get("/tasks/{task_id}", response_model=TaskResponse)
def get_task(task_id: int):
    return {"task_id": task_id}
```

通常响应是：

```json
{
  "task_id": 101,
  "status": "pending",
  "answer": null,
  "tags": []
}
```

为什么？

因为 Pydantic 会为未提供的字段填入模型规定的默认值。

但假设你不想把所有没有显式设置过的字段都返回给前端。

就可以写：

```python
@app.get(
    "/tasks/{task_id}",
    response_model=TaskResponse,
    response_model_exclude_unset=True
)
def get_task(task_id: int):
    return {"task_id": task_id}
```

现在响应可以只包含：

```json
{
  "task_id": 101
}
```

### 1. exclude_unset 具体是什么意思？

拆开英文：

- `exclude`：排除。
- `unset`：未显式设置。

因此：

**`response_model_exclude_unset=True` 会在输出时排除没有显式设置过的字段。**

并不是简单地“删除所有值为 None 的字段”，也不是“删除所有等于默认值的字段”。

### 2. 三个相似选项的区别

| 参数 | 排除什么？ |
|---|---|
| `response_model_exclude_unset=True` | 没有显式设置的字段 |
| `response_model_exclude_none=True` | 值为 `None` 的字段 |
| `response_model_exclude_defaults=True` | 值等于默认值的字段 |

例如：

```python
return {
    "task_id": 101,
    "status": "pending",
    "answer": None
}
```

虽然 status 是默认值 `"pending"`，但是这里**显式提供了 status**。

因此：

- `exclude_unset=True`：仍会保留 status 和 answer，省略未设置的 tags。
- `exclude_none=True`：排除 answer，因为它是 None。
- `exclude_defaults=True`：会排除与默认值相等的 status、answer 和 tags。

这些参数之间的区别，官方响应模型教程有专门的示例。

### 🤖 Agent 项目中怎么用？

Agent 执行器可能有多种状态：

```text
pending → running → completed
```

尚未执行完成时，可能只有：

```json
{
  "task_id": 101,
  "status": "pending"
}
```

执行完成后：

```json
{
  "task_id": 101,
  "status": "completed",
  "answer": "这是 Agent 的最终回答"
}
```

如果你希望响应中只包含当前已经明确设置的字段，可以考虑 `response_model_exclude_unset=True`。

但一定要和前端约定好：**某些字段可能完全不存在，而不是存在且为 null。**

## 七、`response_model_include` 和 `response_model_exclude`

FastAPI 还提供两个功能：

```python
response_model_include={"name", "price"}
```

和：

```python
response_model_exclude={"internal_notes"}
```

看一个例子：

```python
class AgentResult(BaseModel):
    answer: str
    agent_id: int
    internal_notes: str


@app.get(
    "/demo",
    response_model=AgentResult,
    response_model_exclude={"internal_notes"}
)
def demo():
    return {
        "answer": "你好",
        "agent_id": 2,
        "internal_notes": "仅供内部使用"
    }
```

返回时会排除 `internal_notes`。

不过，**这里有一个重要的工程问题**。

虽然实际响应中可以排除字段，但 OpenAPI 文档里的响应模型 Schema 仍可能描述完整的 `AgentResult`，包括 `internal_notes`。

因此，官方更推荐：

**直接创建一个不包含敏感字段的独立输出模型。**

例如：

```python
class AgentResultOut(BaseModel):
    answer: str
    agent_id: int
```

然后：

```python
@app.get("/demo", response_model=AgentResultOut)
```

这样响应结构和 API 文档都更加明确。

这也正好引出了下一章的《更多模型》。

## 八、`response_model=None` 是什么？

默认情况下，FastAPI 会尝试根据函数的有效返回类型注解生成响应模型。

但有些时候，函数可能直接返回特殊的响应对象，或者你不希望自动生成响应模型。

可以设置：

```python
@app.get("/demo", response_model=None)
def demo():
    return {"message": "hello"}
```

这里的：

```python
response_model=None
```

表示**关闭该路由的自动响应模型生成**。

它不是：

```python
response_model=ChatResponse
```

的替代品，也不意味着禁用所有 HTTP 响应。

你现在只需要知道：

- 普通 Agent JSON API：优先明确声明响应模型。
- 特殊返回类型：某些情况下可以使用 `response_model=None`。
- 如果需要直接返回 `Response`、`JSONResponse` 等对象，还要学习它们各自的处理方式。

这是官方教程的进阶内容，现阶段不用急着深入。

## 九、第一章 Agent 实战：让返回数据符合 ChatResponse

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


# 请求模型
class ChatRequest(BaseModel):
    message: str = Field(
        min_length=1,
        max_length=2000
    )

    max_steps: int = Field(
        default=3,
        ge=1,
        le=5
    )


# 响应模型
class ChatResponse(BaseModel):
    answer: str
    agent_id: int
    steps: list[str] = Field(default_factory=list)


@app.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest):

    steps = [
        "理解用户问题",
        "制定计划",
        "生成模拟回答"
    ]

    result = {
        "answer": f"Agent 收到了：{request.message}",
        "agent_id": 2,
        "steps": steps[:request.max_steps],

        # 内部字段，不属于 ChatResponse
        "internal_debug": "内部调试信息"
    }

    return result
```

运行：

```bash
fastapi dev main.py
```

打开：

```text
http://127.0.0.1:8000/docs
```

提交：

```json
{
  "message": "请解释 FastAPI",
  "max_steps": 2
}
```

预期响应：

```json
{
  "answer": "Agent 收到了：请解释 FastAPI",
  "agent_id": 2,
  "steps": [
    "理解用户问题",
    "制定计划"
  ]
}
```

你会发现：

```python
"internal_debug": "内部调试信息"
```

没有出现在最终 JSON 中。

原因就是：

```python
response_model=ChatResponse
```

仅允许按照 `ChatResponse` 声明的字段输出。

注意：`steps` 在这里只是模拟步骤列表，还没有真正调用 LangGraph。

### 第一章参考答案

| 题号 | 答案 | 原因 |
|---|---|---|
| 1 | B | response_model 是路由装饰器的参数 |
| 2 | C | 客户端输入验证失败通常返回 422 |
| 3 | D | 服务端响应验证失败通常返回 500 |
| 4 | B | 根据输出模型过滤未声明字段 |
| 5 | C | 排除未显式设置的字段 |
| 6 | B | 独立输出模型使 API 契约更清晰 |
