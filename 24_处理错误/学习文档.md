# 第一章：处理错误（Handling Errors）

## 一、HTTP 错误与正常响应

之前你写过这样的代码：

```python
@app.get("/agents/{agent_id}")
def get_agent(agent_id: int):
    return {
        "agent_id": agent_id,
        "name": "Chat Agent"
    }
```

如果访问：

```text
GET /agents/1
```

可以正常返回：

```json
{
  "agent_id": 1,
  "name": "Chat Agent"
}
```

但是，这段代码存在一个业务问题：

即使用户访问：

```text
GET /agents/999
```

它仍然会返回一个 Agent。

因为我们没有检查这个 Agent 是否真的存在。

现在假设系统里只有两个 Agent：

```python
agents = {
    1: "Chat Agent",
    2: "Code Agent"
}
```

当用户请求 Agent 999 时，后端就应该明确告诉客户端：

> 你要访问的资源不存在。

HTTP 协议已经定义了一套状态码来表达不同的处理结果。

| 状态码 | 含义 | Agent 开发中的例子 |
|---|---|---|
| 200 | OK，成功 | 查询 Agent 成功 |
| 201 | Created，已创建 | 新建 Agent 成功 |
| 400 | Bad Request，请求不符合业务要求 | 请求了当前 Agent 不支持的配置 |
| 401 | Unauthorized，未通过身份认证 | 未提供有效登录凭据 |
| 403 | Forbidden，没有访问权限 | 用户无权访问某个 Agent |
| 404 | Not Found，资源不存在 | Agent ID 不存在 |
| 422 | Unprocessable Content，请求数据验证失败 | `max_steps` 超出规定范围 |
| 500 | Internal Server Error，服务器内部错误 | 后端程序自身发生异常 |
| 503 | Service Unavailable，服务暂时不可用 | Agent 服务暂时无法处理请求 |

这里需要建立一个概念：

**HTTP 状态码用于告诉客户端请求的处理结果；JSON 响应体用于补充具体数据或错误说明。**

这两部分不是同一个东西。

## 二、HTTPException：主动返回 HTTP 错误

FastAPI 提供了一个专门的类：

```python
HTTPException
```

它用于在代码中主动产生 HTTP 错误响应。

这是官方教程的基本写法。

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

items = {
    "foo": "The Foo Wrestlers"
}


@app.get("/items/{item_id}")
async def read_item(item_id: str):

    if item_id not in items:
        raise HTTPException(
            status_code=404,
            detail="Item not found"
        )

    return {
        "item": items[item_id]
    }
```

### 1. 代码逐行拆解

先定义一个字典：

```python
items = {
    "foo": "The Foo Wrestlers"
}
```

表示当前存在一个 ID 为 `foo` 的项目。

然后：

```python
@app.get("/items/{item_id}")
```

表示用户可以通过路径传入一个项目 ID。

例如：

```text
/items/foo
/items/bar
```

接下来：

```python
if item_id not in items:
```

检查用户请求的项目是否在字典里。

如果不存在：

```python
raise HTTPException(
    status_code=404,
    detail="Item not found"
)
```

这里最重要的两个参数是：

| 参数 | 含义 |
|---|---|
| `status_code=404` | 告诉客户端资源不存在 |
| `detail="Item not found"` | 提供错误的具体说明 |

### 2. 请求存在的项目

访问：

```text
GET /items/foo
```

返回：

  
  **HTTP 200**

```json
{
  "item": "The Foo Wrestlers"
}
```

### 3. 请求不存在的项目

访问：

```text
GET /items/bar
```

返回：

  
  **HTTP 404**

```json
{
  "detail": "Item not found"
}
```

注意：

```python
detail="Item not found"
```

最终会出现在 JSON 的：

```json
"detail"
```

字段中。

这是 FastAPI 默认的 HTTPException 错误响应结构。

## 三、`raise` 与 `return` 的区别 ⭐⭐⭐

这是第一章最重要的知识点。

你已经非常熟悉：

```python
return
```

它表示函数返回一个值。

例如：

```python
return {
    "answer": "你好"
}
```

但 `HTTPException` 是一种 Python 异常。

所以应该使用：

```python
raise HTTPException(...)
```

而不是：

```python
return HTTPException(...)
```

### 1. 正确的错误处理

```python
@app.get("/agents/{agent_id}")
def get_agent(agent_id: int):

    if agent_id != 1:
        raise HTTPException(
            status_code=404,
            detail="Agent not found"
        )

    return {
        "agent_id": 1,
        "name": "Chat Agent"
    }
```

当用户请求不存在的 Agent 时：

```python
raise HTTPException(...)
```

会中断当前正常执行流程。

FastAPI 捕获这个异常后，将它转换成 HTTP 错误响应。

因此，后面的正常 `return` 不再执行。

### 2. 不推荐的写法

```python
@app.get("/agents/{agent_id}")
def get_agent(agent_id: int):

    if agent_id != 1:
        return {
            "error": "Agent not found"
        }

    return {
        "agent_id": 1
    }
```

虽然客户端收到了：

```json
{
  "error": "Agent not found"
}
```

但如果没有另外设置响应状态码，它通常仍然是：

**HTTP 200！**

这就出现了一个矛盾：

- JSON 说发生错误。
- HTTP 状态码却说请求成功。

前端代码可能根据状态码将其误判成正常结果。

因此：

**需要返回标准 HTTP 错误时，优先使用 `raise HTTPException(...)`。**

### 3. 与普通 Python 异常的联系

你以后可能写：

```python
raise ValueError("Invalid value")
```

或者：

```python
raise RuntimeError("Something went wrong")
```

它们同样使用 `raise`。

区别是 `HTTPException` 专门携带 HTTP 状态码等信息，FastAPI 知道怎样把它转换成 HTTP 响应。

普通 Python 异常如果没有被处理，通常会导致服务器错误，而不会自动转换成你希望的 404 或 400。

## 四、客户端输入错误与业务错误

结合你之前学过的 Pydantic，可以把错误分成两大类。

### 第一类：输入校验错误

例如：

```python
from pydantic import BaseModel, Field


class ChatRequest(BaseModel):
    message: str = Field(min_length=1)
    max_steps: int = Field(default=3, ge=1, le=5)
```

客户端提交：

```json
{
  "message": "",
  "max_steps": 9
}
```

其中：

- `message` 不符合最小长度要求。
- `max_steps` 超过最大允许值 5。

FastAPI 会在进入业务函数之前验证请求。

验证失败通常自动返回：

**HTTP 422。**

你不需要为每一个 `Field()` 手写 `HTTPException(422)`。

### 第二类：业务判断错误

例如用户提交的 JSON 完全合法：

```json
{
  "message": "请解释 Python",
  "max_steps": 3
}
```

但路径里指定的 Agent 不存在：

```text
POST /agents/999/chat
```

这种情况不是 Pydantic 字段格式有问题。

而是：

**用户请求的业务资源不存在。**

所以需要你的代码主动判断：

```python
if agent_id not in agents:
    raise HTTPException(
        status_code=404,
        detail="Agent not found"
    )
```

### 两类错误的处理位置

  

    **客户端向 FastAPI 发送请求**
    
Path、Query、Body、Cookie、Header、Form、File

  

  

    **FastAPI / Pydantic 验证输入**
    
字段缺失、类型不符、范围错误 → 通常 422

  

  

    **执行业务函数**
    
Agent 不存在 → 主动 raise HTTPException(404)

  

  

    **返回正常结果**
    
完成任务 → 通常返回 200，创建成功可使用 201

还有一种你在上一章《响应模型－返回类型》中学过的错误：

**如果请求合法，但服务器返回的数据不符合响应模型，则通常属于服务器自身错误，返回 500，而不是 422。**

## 五、HTTPException 的更多用法

### 1. detail 可以是字典

前面的例子：

```python
raise HTTPException(
    status_code=404,
    detail="Agent not found"
)
```

其中 `detail` 是字符串。

但在真实 Agent 项目中，你可能希望错误信息更有结构。

例如：

```python
raise HTTPException(
    status_code=404,
    detail={
        "code": "AGENT_NOT_FOUND",
        "message": "Agent 999 不存在"
    }
)
```

客户端得到：

```json
{
  "detail": {
    "code": "AGENT_NOT_FOUND",
    "message": "Agent 999 不存在"
  }
}
```

这里出现了两个不同的概念：

- `status_code=404`：标准 HTTP 错误状态。
- `code="AGENT_NOT_FOUND"`：你自己设计的业务错误编号。

以后前端可以根据业务错误编号决定显示怎样的提示。

FastAPI 的 `HTTPException.detail` 可以接受字符串、字典、列表等能够转换为 JSON 的数据。

### 2. 给错误响应增加 Header

例如：

```python
raise HTTPException(
    status_code=404,
    detail="Agent not found",
    headers={
        "X-Error-Code": "AGENT_NOT_FOUND"
    }
)
```

此时 HTTP 响应分成两部分：

**响应头：**

```http
HTTP/1.1 404 Not Found
X-Error-Code: AGENT_NOT_FOUND
```

**响应体：**

```json
{
  "detail": "Agent not found"
}
```

这与你之前学习的 Header 参数正好形成对应：

- `Header()`：读取客户端的请求头。
- `HTTPException(headers=...)`：为服务器的错误响应添加响应头。

不过，一般的简单业务错误只使用 `status_code` 和 `detail` 就够了，不需要每次都增加自定义 Header。

## 六、自定义异常处理器

这是官方教程中相对进阶的部分，我们用 Agent 场景来理解。

假设你的 Agent 执行器有时暂时无法提供服务。

你不希望每一个调用它的接口都重复写：

```python
raise HTTPException(
    status_code=503,
    detail="Agent temporarily unavailable"
)
```

而是希望在业务层表达：

> Agent 当前不可用。

并让一个统一的位置负责将这类业务异常转换成 HTTP 响应。

这就需要**自定义异常和异常处理器**。

### 1. 定义业务异常

```python
class AgentUnavailableError(Exception):

    def __init__(self, agent_id: int):
        self.agent_id = agent_id
```

这里的：

```python
Exception
```

是 Python 的异常基类。

```python
AgentUnavailableError
```

是我们自己定义的异常类型。

它保存一个：

```python
agent_id
```

用来说明哪个 Agent 发生问题。

### 2. 注册异常处理器

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(AgentUnavailableError)
async def unavailable_handler(
    request: Request,
    exc: AgentUnavailableError
):
    return JSONResponse(
        status_code=503,
        content={
            "error": {
                "code": "AGENT_UNAVAILABLE",
                "message": "Agent 暂时不可用"
            }
        }
    )
```

关键代码：

```python
@app.exception_handler(AgentUnavailableError)
```

意思是：

> 当应用中出现尚未被其他地方处理的 AgentUnavailableError 时，由这个函数统一处理。

函数参数：

```python
request: Request
```

表示当前 HTTP 请求对象。

```python
exc: AgentUnavailableError
```

表示发生的异常对象。

然后：

```python
JSONResponse(...)
```

明确创建一个 JSON HTTP 响应。

它与你之前学习的：

```python
response_model=ChatResponse
```

不同。这里是直接创建一个特殊的错误响应。

官方教程使用相同的机制处理自定义 Python 异常。

### 3. 在业务代码中触发自定义异常

```python
@app.get("/agents/2/run")
def run_agent():

    raise AgentUnavailableError(agent_id=2)
```

执行流程：

```text
客户端请求 /agents/2/run
            ↓
业务函数运行
            ↓
raise AgentUnavailableError
            ↓
FastAPI 找到注册的异常处理器
            ↓
unavailable_handler() 创建 JSONResponse
            ↓
客户端收到 HTTP 503
```

客户端收到：

```json
{
  "error": {
    "code": "AGENT_UNAVAILABLE",
    "message": "Agent 暂时不可用"
  }
}
```

注意，这里的响应字段是：

```json
"error"
```

而不是默认 HTTPException 中的：

```json
"detail"
```

因为**自定义异常处理器可以自己定义响应结构**。

## 七、覆盖 FastAPI 默认的错误处理器

你之前看到过很多次 HTTP 422。

例如：

```json
{
  "detail": [
    {
      "type": "greater_than_equal",
      "loc": ["body", "max_steps"],
      "msg": "Input should be greater than or equal to 1"
    }
  ]
}
```

这类错误来自 FastAPI 的请求验证机制。

FastAPI 内部会使用：

```python
RequestValidationError
```

表示请求数据验证失败。

通常你不用手工处理它，因为 FastAPI 已经内置了默认处理器。

但如果以后你的公司要求所有接口统一使用：

```json
{
  "error": "INVALID_INPUT",
  "details": [...]
}
```

这种格式，可以覆盖默认处理器。

下面是独立的进阶示例：

```python
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(RequestValidationError)
async def validation_handler(
    request: Request,
    exc: RequestValidationError
):
    errors = [
        {
            "loc": list(error["loc"]),
            "msg": error["msg"]
        }
        for error in exc.errors()
    ]

    return JSONResponse(
        status_code=422,
        content={
            "error": "INVALID_INPUT",
            "details": errors
        }
    )
```

最重要的一行：

```python
@app.exception_handler(RequestValidationError)
```

表示为请求验证异常注册新的处理方式。

`exc.errors()` 会提供验证错误的详细信息。

这里仍然使用：

```python
status_code=422
```

因为我们只是改变错误响应的格式，没有改变“客户端请求验证失败”的性质。

**注意：注册这个处理器会影响整个 FastAPI 应用中的请求验证错误，不只是某一个路由。** 本节用来理解机制，暂时不必在所有练习项目中启用。

此外，真实项目不要随意把异常对象、完整请求体、密码、令牌等敏感信息返回客户端。

### FastAPI HTTPException 与 Starlette HTTPException

官方教程还介绍了一个进阶细节：

FastAPI 基于 Starlette 构建。FastAPI 的 `HTTPException` 继承自 Starlette 的 `HTTPException`。

如果以后需要统一覆盖包括框架内部 404 在内的 HTTP 异常，通常应该注册：

```python
from starlette.exceptions import (
    HTTPException as StarletteHTTPException
)


@app.exception_handler(StarletteHTTPException)
async def custom_http_handler(request, exc):
    ...
```

这样既能处理 FastAPI 抛出的 HTTPException，也能处理来自 Starlette 的相关 HTTP 异常。

但现阶段：

**写普通业务接口时，先熟练掌握 `raise HTTPException(...)`；自定义异常处理器属于下一层的工程组织能力。**

## 八、Agent 综合实战：区分 200、400、404、422 和 503

下面这个案例最适合把本章知识放到一起。

系统中有两个模拟 Agent：

```python
AGENTS = {
    1: "Chat Agent",
    2: "Code Agent"
}
```

请求模型：

```python
class ChatRequest(BaseModel):
    message: str = Field(min_length=1)
    max_steps: int = Field(default=3, ge=1, le=5)
```

业务规则：

- Agent 1 是普通聊天 Agent，最多允许 3 步。
- Agent 2 是代码 Agent，演示一种暂时不可用的异常。
- 不存在的 Agent 应返回 404。

核心接口可以这样写：

```python
@app.post("/agents/{agent_id}/chat")
def chat(
    agent_id: int,
    request: ChatRequest
):

    # Agent 不存在
    if agent_id not in AGENTS:
        raise HTTPException(
            status_code=404,
            detail="Agent not found"
        )

    # 通用请求模型允许 1～5 步，
    # 但 Chat Agent 的业务规则只允许最多 3 步
    if agent_id == 1 and request.max_steps > 3:
        raise HTTPException(
            status_code=400,
            detail="Chat Agent supports at most 3 steps"
        )

    # 模拟 Agent 暂时不可用
    if agent_id == 2 and request.message == "busy":
        raise AgentUnavailableError(agent_id=2)

    return {
        "answer": f"Agent 收到了：{request.message}"
    }
```

其中 `AgentUnavailableError` 使用前面注册的异常处理器。

### 逐个测试

| 请求 | 结果 | 原因 |
|---|---|---|
| POST `/agents/1/chat`，message=你好，max_steps=2 | 200 | 请求和业务规则都合法 |
| POST `/agents/1/chat`，message="" | 422 | Pydantic 字符串长度校验失败 |
| POST `/agents/1/chat`，max_steps=9 | 422 | 超出通用模型的最大值 5 |
| POST `/agents/1/chat`，max_steps=4 | 400 | 通用模型允许 4，但 Agent 1 的业务规则最多 3 |
| POST `/agents/999/chat`，其他参数合法 | 404 | Agent 不存在 |
| POST `/agents/2/chat`，message=busy | 503 | 模拟触发自定义不可用异常 |

其中最值得思考的是：

**为什么 max_steps=4 返回 400，而 max_steps=9 返回 422？**

因为它们是在不同阶段被拒绝的。

- `9`：违反 Pydantic 的 `Field(le=5)`，请求进入业务代码前就被拒绝。
- `4`：符合 Pydantic 的 1～5 约束，但违反 Agent 1 特有的业务规则，所以业务函数主动返回 400。

这正是**输入结构验证**与**业务规则判断**的区别。

这里选择 400 是一种明确的 API 设计，并不是所有业务规则失败都必须使用 400。具体状态码应根据错误语义确定。

## 九、第一章常见错误

| 常见写法或理解 | 问题 | 正确思路 |
|---|---|---|
| `return {"error": "不存在"}` | 默认可能仍返回 200 | 使用 `raise HTTPException(404, ...)` |
| `return HTTPException(...)` | 把异常当返回值 | 使用 `raise` |
| 所有错误一律返回 500 | 混淆客户端错误与服务器错误 | 按错误性质选择状态码 |
| 所有错误一律返回 422 | 混淆 Pydantic 校验和业务判断 | 字段校验通常自动 422，业务错误显式处理 |
| `except Exception` 后全部转成 400 | 容易隐藏真正的服务器程序错误 | 只捕获你能合理处理的异常 |
| 把异常堆栈、密钥返回前端 | 泄露内部实现或敏感信息 | 返回清晰、有限的公开错误信息 |

另一个跨章节知识点：**`response_model` 的输出校验失败通常属于服务器错误，不是 `RequestValidationError`。**

所以不要把所有 500 错误都通过请求验证处理器改成 422。

### 第一章答案与解析

| 题号 | 答案 | 具体原因 |
|---|---|---|
| 1 | B | HTTPException 配合 raise 产生 HTTP 错误 |
| 2 | B | detail 提供错误说明 |
| 3 | A | raise 使正常控制流转入异常处理 |
| 4 | C | Field 的范围验证失败，通常 422 |
| 5 | B | 资源是否存在是业务判断 |
| 6 | A | exception_handler 注册异常处理函数 |
| 7 | C | RequestValidationError 表示请求校验错误 |
| 8 | B | headers 用于添加错误响应头 |

**思考题 1：** `9` 超出模型规定的上限 5，Pydantic 在请求验证阶段拒绝，通常返回 422。`4` 通过模型校验，但超过某个 Agent 特定的 3 步业务上限，可以由业务代码主动返回 400。

**思考题 2：** 不会执行 `run_agent()`。`raise HTTPException(...)` 会中断后续正常代码；客户端收到 HTTP 404，默认 JSON 为 `{"detail":"Agent not found"}`。
