# 📘 FastAPI 查询参数模型：零基础完整讲解

## 一、这章到底要解决什么问题？

### 1. 我们之前的 Agent API 有什么不足？

回忆上一章，我们写过这样的接口：

```python
@app.get("/agents/")
def get_agents(
    limit: Annotated[
        int, Query(ge=1, le=100)
    ] = 10,

    offset: Annotated[
        int, Query(ge=0)
    ] = 0,

    order_by: str = "created_at",

    tag: Annotated[
        list[str], Query()
    ] = []
):
    ...
```

它虽然能运行，但存在一个问题：

**当查询参数越来越多时，函数参数列表会越来越长。**

将来开发 Agent 管理系统，可能会出现：

```text
limit
offset
order_by
tags
status
model_name
created_after
created_before
```

如果每个接口都写这些参数，就会导致：

- 很多重复代码。
- 每个接口的默认值可能不一致。
- 修改参数规则时需要同时修改多个地方。
- 很难复用参数定义。
- 团队协作时不容易维护。

所以官方提出一种更好的方法：

**把相关查询参数统一放进一个 Pydantic 模型，然后通过 Query() 告诉 FastAPI，这个模型中的字段都来自查询参数。**

### 2. 核心变化：从零散参数到模型

  

      

之前的写法

        
`limit: int = 10`

`offset: int = 0`

`order_by: str = ...`

`tags: list[str] = ...`

        
每个接口重复声明多个参数

    

      

本章的新写法

        

          
FilterParams

封装全部字段

        

多个接口可以重复使用同一模型

    

  

    
将相关参数集中管理

  

    **`filter_query: Annotated[FilterParams, Query()]`**
    
用一个函数参数接收一组查询条件

### 🤖 对 Agent 开发有什么意义？

我们先明确一点：

**Agent 系统中不只有“向大模型提问”这一种 API。**

一个真实的 Agent 平台通常还需要其他接口。

| Agent 功能 | API 示例 | 查询参数模型的作用 |
|---|---|---|
| 查询 Agent 列表 | `GET /agents/` | 分页、排序、标签筛选 |
| 查询 Agent 任务 | `GET /tasks/` | 筛选执行状态和创建时间 |
| 查询对话记录 | `GET /sessions/` | 按会话、日期、分页查询 |
| 搜索知识库文档 | `GET /documents/` | 关键词、文档类别、分页 |
| 查看工具日志 | `GET /tool-logs/` | 按工具类型、时间、结果筛选 |

所以，本章的知识主要用于 **Agent 平台的查询、管理和接口工程化**。

而你之前学习的请求体 `ChatRequest`，主要用于向 Agent 提交用户任务。

后面我们会把这两部分放在同一个系统中，理解它们各自的职责。

## 二、官方核心代码：使用 Pydantic 模型声明查询参数

这是整章最重要的代码。

建议你先完整看一遍，不要求马上全部理解。

```python
from typing import Annotated, Literal

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()


class FilterParams(BaseModel):
    limit: int = Field(100, gt=0, le=100)

    offset: int = Field(0, ge=0)

    order_by: Literal[
        "created_at",
        "updated_at"
    ] = "created_at"

    tags: list[str] = []


@app.get("/items/")
async def read_items(
    filter_query: Annotated[FilterParams, Query()]
):
    return filter_query
```

这就是 FastAPI 官方教程的基础示例，适用于 Python 3.10 及以上版本。

**注意版本要求：查询参数模型从 FastAPI `0.115.0` 开始支持。** 如果你的环境过旧，需要升级才能使用这一特性。

### 1. 先认识本章新出现的 Literal

官方代码导入：

```python
from typing import Annotated, Literal
```

`Annotated` 我们已经学过。

现在的新知识是：

```python
Literal
```

它来自 Python 标准库 `typing`，可以用于描述某个值只能是指定的几个字面值之一。

例如：

```python
order_by: Literal[
    "created_at",
    "updated_at"
]
```

意思是：

`order_by` 只允许下面两个字符串：

```text
created_at
updated_at
```

不能随便传：

```text
price
name
hello
```

### 2. Literal 和之前学过的 Enum 有什么区别？

你还记得《路径参数》一章学过：

```python
from enum import Enum

class AgentType(str, Enum):
    chat = "chat"
    code = "code"
```

Enum 也可以限制固定选项。

对比一下：

| 对比 | Literal | Enum |
|---|---|---|
| 主要用途 | 描述允许的具体值 | 定义可以复用的枚举类型 |
| 代码 | `Literal["chat", "code"]` | `class AgentType(str, Enum)` |
| 校验不合法输入 | ✅ | ✅ |
| 是否需要额外定义类 | 不需要 | 需要 |
| 适用场景 | 简单固定选项 | 多处复用、有业务含义的选项 |

对于这一章的 `order_by`，只有两个候选值，使用 `Literal` 很直观。

你可以这样记忆：

**Literal 是规定允许哪些具体值；Enum 是定义一组有名称的固定选项。**

这两种写法在 FastAPI 中都能够辅助数据校验和自动文档生成。

## 三、逐行拆解 FilterParams：模型中的每一个字段

我们把官方模型单独拿出来：

```python
class FilterParams(BaseModel):
    limit: int = Field(100, gt=0, le=100)
    offset: int = Field(0, ge=0)
    order_by: Literal[
        "created_at",
        "updated_at"
    ] = "created_at"
    tags: list[str] = []
```

这四个字段其实对应四种很常见的 API 功能：

| 字段 | 作用 |
|---|---|
| `limit` | 返回多少条数据 |
| `offset` | 跳过前多少条数据 |
| `order_by` | 按哪个字段排序 |
| `tags` | 按哪些标签筛选 |

下面逐个解释。

### 1. limit：控制返回的数据数量

```python
limit: int = Field(100, gt=0, le=100)
```

拆成四部分：

| 代码 | 含义 |
|---|---|
| `limit` | 字段名称 |
| `int` | 必须是整数 |
| `100` | 默认值为 100 |
| `gt=0` | 必须大于 0 |
| `le=100` | 必须小于或等于 100 |

数学上：

\[
0 < \text{limit} \leq 100
\]

因此：

| limit 的值 | 是否合法 |
|---|---|
| 1 | ✅ |
| 10 | ✅ |
| 100 | ✅ |
| 0 | ❌ |
| -1 | ❌ |
| 101 | ❌ |

**一个小白特别需要注意的地方：**

在以前的单个查询参数中，我们通常写：

```python
limit: Annotated[
    int,
    Query(gt=0, le=100)
] = 100
```

而现在写：

```python
limit: int = Field(100, gt=0, le=100)
```

为什么从 `Query` 变成了 `Field`？

因为现在的 `limit` 是 **Pydantic 模型的字段**，我们通过 `Field()` 为这个字段设置默认值和验证规则。

而模型整体：

```python
Annotated[FilterParams, Query()]
```

负责告诉 FastAPI：这些字段要从 HTTP 查询参数中提取。

这两个工具分工不同。

### 2. offset：跳过多少条数据

```python
offset: int = Field(0, ge=0)
```

其中：

- `offset`：参数名称。
- `int`：整数类型。
- `0`：默认不跳过任何数据。
- `ge=0`：允许 0，但不允许负数。

假设有五个 Agent：

```python
agents = [
    "Chat Agent",
    "Code Agent",
    "Research Agent",
    "Math Agent",
    "Travel Agent"
]
```

用户传入：

```text
?offset=2&limit=2
```

你可以使用 Python 切片：

```python
agents[2:4]
```

得到：

```python
[
    "Research Agent",
    "Math Agent"
]
```

这就是常见的**分页（Pagination）**思路。

你之前已经学过 `skip` 和 `limit`。

这里的 `offset` 可以理解为类似的跳过条数。

### 3. order_by：控制排序字段

```python
order_by: Literal[
    "created_at",
    "updated_at"
] = "created_at"
```

这行的意思是：

> 用户可以选择按创建时间排序，也可以按更新时间排序；如果不传，默认按创建时间排序。

因此：

```text
/items/?order_by=created_at
```

✅ 合法。

```text
/items/?order_by=updated_at
```

✅ 合法。

```text
/items/?order_by=price
```

❌ 返回 HTTP 422，因为 `price` 不在允许的列表中。

注意：这里的 `order_by` 只指定**排序字段**，并没有规定升序还是降序。

也就是说，如果以后需要：

```text
sort_direction=desc
```

还需要再设计一个对应的参数，或者在业务代码中确定排序方向。

### 4. tags：接收多个标签

```python
tags: list[str] = []
```

我们上一章已经学过 `list[str]`。

它表示一个由字符串组成的列表。

例如：

```python
["python", "research"]
```

当客户端访问：

```text
/items/?tags=python&tags=research
```

FastAPI 会把多个同名查询参数收集起来：

```python
tags = ["python", "research"]
```

如果没有传 `tags`，模型使用默认的空列表：

```python
tags = []
```

官方使用了：

```python
tags: list[str] = []
```

这是可以工作的。Pydantic 会妥善处理这种非哈希的可变默认值，不会简单地让所有模型实例共享同一个可变列表。

不过在实际项目中，我建议你养成使用下面这种写法的习惯：

```python
tags: list[str] = Field(default_factory=list)
```

这里：

```python
default_factory=list
```

表示在需要默认值时创建一个新列表。

这也是 Python 数据模型中更明确、便于维护的习惯。

## 四、最核心的一行：Annotated[FilterParams, Query()]

现在终于来到本章的灵魂代码：

```python
@app.get("/items/")
def read_items(
    filter_query: Annotated[
        FilterParams,
        Query()
    ]
):
    return filter_query
```

你需要彻底理解这一行：

```python
filter_query: Annotated[FilterParams, Query()]
```

### 1. 把它拆成四个部分

  

    **① `filter_query`**
    
函数参数的名称，它将接收一个 Pydantic 模型实例。

  

    **② `FilterParams`**
    
我们之前定义的 Pydantic 模型，内部包含 limit、offset、order_by、tags。

  

    **③ `Query()`**
    
明确告诉 FastAPI，从 URL 查询参数中读取模型字段。

  

    **④ `Annotated[...]`**
    
把类型与 FastAPI 的参数来源声明组织在一起。

整句话的意思是：

> FastAPI，请从 URL 的查询参数中读取 limit、offset、order_by 和 tags，并使用这些数据创建一个 FilterParams 对象，再把它传给 filter_query。

### 2. FastAPI 到底如何处理请求？

假设用户访问：

```text
GET /items/?limit=10&offset=5&order_by=updated_at&tags=python&tags=ai
```

首先，FastAPI 从 URL 中提取：

```python
limit = 10
offset = 5
order_by = "updated_at"
tags = ["python", "ai"]
```

然后，根据 Pydantic 模型，创建相当于下面的对象：

```python
filter_query = FilterParams(
    limit=10,
    offset=5,
    order_by="updated_at",
    tags=["python", "ai"]
)
```

这时你就能使用：

```python
filter_query.limit
filter_query.offset
filter_query.order_by
filter_query.tags
```

最后，官方代码直接：

```python
return filter_query
```

于是 FastAPI 返回：

```json
{
  "limit": 10,
  "offset": 5,
  "order_by": "updated_at",
  "tags": ["python", "ai"]
}
```

### 3. 用图理解整个过程

  

    **① 用户发送 GET 请求**
    
`?limit=10&offset=5&order_by=updated_at`

  

  

    **② FastAPI 识别 Query()**
    
确定数据来自 URL 查询字符串

  

  

    **③ Pydantic 检查 FilterParams**
    
验证类型、范围、固定选项并填充默认值

  

  

    **④ 创建模型实例**
    
`filter_query = FilterParams(...)`

  

  

    **⑤ 执行接口中的 Python 逻辑**
    
`filter_query.limit` 等

这里最关键的结论是：

**模型的名字叫 FilterParams，函数参数叫 filter_query，但 URL 中仍然直接使用 limit、offset、order_by、tags。**

不需要写成：

```text
?filter_query.limit=10
```

也不需要提交 JSON 请求体。

这仍然是一个正常的 GET 查询接口。

### 4. 与上一章请求体的 BaseModel 有什么区别？

这是我特别希望你真正理解的地方。

你之前写过：

```python
class ChatRequest(BaseModel):
    message: str
```

然后：

```python
@app.post("/chat")
def chat(request: ChatRequest):
    ...
```

这是从请求体读取数据。

而本章：

```python
class FilterParams(BaseModel):
    limit: int = 10
```

然后：

```python
@app.get("/items/")
def get_items(
    filters: Annotated[FilterParams, Query()]
):
    ...
```

这是从查询参数读取数据。

| 对比 | 请求体模型 | 查询参数模型 |
|---|---|---|
| 都继承 BaseModel | ✅ | ✅ |
| 都能使用 Field | ✅ | ✅ |
| 都有 Pydantic 校验 | ✅ | ✅ |
| 数据从哪里读取 | HTTP 请求体 | URL 查询字符串 |
| 典型用途 | 提交 Agent 对话 | 查询 Agent 列表 |

因此，千万不要认为：

**“只要继承 BaseModel，就一定是请求体。”**

这在以前的基础示例中通常成立，但现在你已经学会了用 `Query()` 显式指定模型的数据来源。

## 六、官方第三部分：禁止额外的查询参数

这是非常实用的功能，也是最容易让初学者忽略的一点。

### 1. 默认情况下，多余的参数可能被忽略

假设模型定义：

```python
class FilterParams(BaseModel):
    limit: int = 100
    offset: int = 0
```

用户却访问：

```text
/items/?limit=10&limt=5
```

注意：

```text
limt
```

是错误拼写，我们原本应该写：

```text
limit
```

在 Pydantic 默认的额外字段处理行为下，未声明的 `limt` 通常会被忽略。

这样就有一个潜在问题：

用户以为自己传了某个参数，后端实际上却没有使用它。

### 2. 使用 model_config 禁止额外字段

官方给出的办法是：

```python
model_config = {"extra": "forbid"}
```

完整代码：

```python
from typing import Annotated, Literal

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()


class FilterParams(BaseModel):

    # 不允许额外字段
    model_config = {"extra": "forbid"}

    limit: int = Field(100, gt=0, le=100)

    offset: int = Field(0, ge=0)

    order_by: Literal[
        "created_at",
        "updated_at"
    ] = "created_at"

    tags: list[str] = []


@app.get("/items/")
def read_items(
    filter_query: Annotated[FilterParams, Query()]
):
    return filter_query
```

这里的：

```python
model_config
```

是 Pydantic 用于定义模型配置的特殊类属性。

而：

```python
{"extra": "forbid"}
```

表示不允许额外的字段。

### 3. extra 的三种常见策略

| 配置 | 含义 |
|---|---|
| `"ignore"` | 忽略未声明的字段，通常是默认行为 |
| `"forbid"` | 拒绝未声明的字段 |
| `"allow"` | 允许并保留额外字段 |

在本章，我们最关心：

```python
"forbid"
```

因为它可以帮助接口更严格地检查客户端传来的参数名称。

### 4. FastAPI 会返回什么错误？

访问：

```text
/items/?limit=10&tool=plumbus
```

但模型中没有定义 `tool`。

由于设置了：

```python
model_config = {"extra": "forbid"}
```

FastAPI 返回 HTTP 422。

官方示例的响应是：

```json
{
  "detail": [
    {
      "type": "extra_forbidden",
      "loc": ["query", "tool"],
      "msg": "Extra inputs are not permitted",
      "input": "plumbus"
    }
  ]
}
```

我们逐个解释：

| 字段 | 含义 |
|---|---|
| `type: extra_forbidden` | 不允许额外字段 |
| `loc: ["query", "tool"]` | 多余的字段是查询参数 tool |
| `msg` | 提示不允许额外输入 |
| `input` | 用户实际提供的值 |

因此，看到这种错误时，你就可以先检查自己有没有拼错查询参数名。

### 🤖 这个功能对 Agent 开发有什么意义？

假设你有一个 Agent 查询接口：

```text
GET /agents/?limit=10
```

但前端误写成：

```text
GET /agents/?limt=10
```

如果后端忽略这个错误，就可能使用默认值，导致实际返回数量不符合预期。

而设置：

```python
model_config = {"extra": "forbid"}
```

以后，就能在接口入口发现这个错误。

不过，不要把它理解成安全防护的全部内容。它不能替代身份验证、授权检查或 Agent 工具的使用权限控制。

还有一个重要提醒：**如果同一个接口要组合多个查询模型，或者额外声明其他查询参数，就要谨慎使用 `extra="forbid"`。** 因为它会检查整个请求的查询参数，其他模型或依赖项声明的字段也可能被认为是当前模型的额外字段。

下一节就会讲这个问题。

## 七、组合多个查询参数模型

这一节在目前的官方英文教程中已经存在，中文版本可能尚未同步。它对 Agent 系统的工程化非常有用。

### 1. 为什么需要多个模型？

假设你现在开发一个 Agent 查询接口，需要两组不同的参数。

第一组：分页参数。

```text
limit
offset
```

第二组：筛选参数。

```text
tags
```

你可以把它们分别定义成两个 Pydantic 模型。

这样，以后其他列表接口也可以使用同一套分页模型。

### 2. 官方完整示例

```python
from typing import Annotated

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()


# 分页参数模型
class Pagination(BaseModel):
    limit: int = Field(10, ge=1)
    offset: int = Field(0, ge=0)


# 标签筛选模型
class Filters(BaseModel):
    tags: list[str] = []


@app.get("/items/")
def read_items(
    pagination: Annotated[Pagination, Query()],
    filters: Annotated[Filters, Query()],
    search: str | None = None,
):
    return {
        "pagination": pagination,
        "filters": filters,
        "search": search
    }
```

这段代码包含三个输入参数：

```python
pagination
filters
search
```

但它们不是三个 JSON 请求体。

这里：

```python
pagination: Annotated[Pagination, Query()]
```

表示从查询字符串中获取 `limit` 和 `offset`。

而：

```python
filters: Annotated[Filters, Query()]
```

表示从查询字符串中获取 `tags`。

最后：

```python
search: str | None = None
```

是普通可选查询参数。

### 3. 实际 URL 是什么样子？

假设访问：

```text
/items/?limit=5&offset=10&tags=python&tags=ai&search=agent
```

FastAPI 会构建：

```python
pagination = Pagination(
    limit=5,
    offset=10
)
```

以及：

```python
filters = Filters(
    tags=["python", "ai"]
)
```

同时：

```python
search = "agent"
```

最终响应：

```json
{
  "pagination": {
    "limit": 5,
    "offset": 10
  },
  "filters": {
    "tags": ["python", "ai"]
  },
  "search": "agent"
}
```

### 4. 为什么 URL 中不需要写 pagination.limit？

这是你必须记住的重点。

我们定义：

```python
pagination: Annotated[Pagination, Query()]
```

并不意味着 URL 必须写成：

```text
?pagination.limit=5
```

而是直接写：

```text
?limit=5
```

同理：

```python
filters: Annotated[Filters, Query()]
```

也不要求：

```text
?filters.tags=python
```

正常写：

```text
?tags=python
```

就可以。

**因为多个查询模型的字段仍然位于同一层 URL 查询字符串中。**

### 5. 为什么这里不使用 extra="forbid"？

因为我们在同一个接口中组合了：

```python
Pagination
Filters
search
```

假设 `Pagination` 设置：

```python
model_config = {"extra": "forbid"}
```

它只知道：

```text
limit
offset
```

但请求中还有：

```text
tags
search
```

这些查询参数就可能被 `Pagination` 视为多余字段而拒绝。

所以在这种组合场景下，要特别小心模型的 extra 配置。

如果多个模型有相同的字段名或别名，也应尽量避免冲突，除非你确实希望它们共同使用同一个查询参数并采用一致的规则。

### 🤖 在 Agent 系统中为什么特别有价值？

你以后可能同时开发：

```text
GET /agents/
GET /tasks/
GET /sessions/
GET /documents/
```

这四个接口都可能需要：

```text
limit
offset
```

所以你不需要为每个接口重复写分页逻辑的参数声明。

可以统一定义：

```python
class Pagination(BaseModel):
    limit: int = Field(10, ge=1, le=100)
    offset: int = Field(0, ge=0)
```

然后在多个 API 中复用。

这就是**后端工程化**的一个重要思想：

**公共能力复用，业务参数独立管理。**

你目前正在从“理解语法”的阶段，逐渐进入“理解 API 如何组织”的阶段。

## 八、可选查询参数模型：整个模型可以不传吗？

答案是：**可以。**

这部分是官方英文新版教程中的另一个知识点。

### 1. 先理解需求

假设你开发一个 Agent 任务日志接口：

```text
GET /task-logs/
```

用户可以选择按日期区间查询。

例如：

```text
/task-logs/?start=2026-10-01&end=2026-10-25
```

但如果用户不需要按日期筛选，就希望直接请求：

```text
/task-logs/
```

这时我们可以让**整组日期参数变成可选模型**。

### 2. 官方示例

```python
from datetime import date
from typing import Annotated

from fastapi import FastAPI, Query
from pydantic import BaseModel

app = FastAPI()


# 日期范围模型
class DateRange(BaseModel):
    start: date
    end: date


@app.get("/items/")
def read_items(
    limit: int = 10,
    date_range: Annotated[
        DateRange | None,
        Query()
    ] = None,
):
    return {
        "limit": limit,
        "date_range": date_range
    }
```

我们重点理解：

```python
date_range: Annotated[
    DateRange | None,
    Query()
] = None
```

### 3. 逐行拆解

**第一层：**

```python
DateRange
```

表示日期范围模型，其中包含：

```python
start: date
end: date
```

两个必填字段。

**第二层：**

```python
DateRange | None
```

表示 `date_range` 可以是 `DateRange` 模型实例，也可以是 `None`。

**第三层：**

```python
Query()
```

告诉 FastAPI 从 URL 查询参数中提取 `start` 和 `end`。

**第四层：**

```python
= None
```

说明整个日期范围模型可以不提供。

### 4. date 是什么？

这是 Python 的日期类型：

```python
from datetime import date
```

它用于表示日期，不包含具体时刻。

例如：

```python
date(2026, 10, 25)
```

在 URL 中通常采用：

```text
2026-10-25
```

这样的 ISO 日期格式。

FastAPI 可以通过 Pydantic 将合法的日期字符串转换为 Python `date` 对象。

### 5. 三种实际请求

**情况 A：完全不传日期**

```text
/items/
```

得到：

```json
{
  "limit": 10,
  "date_range": null
}
```

因为整个日期范围模型的默认值是 `None`。

**情况 B：同时提供 start 和 end**

```text
/items/?start=2026-10-01&end=2026-10-25
```

得到：

```json
{
  "limit": 10,
  "date_range": {
    "start": "2026-10-01",
    "end": "2026-10-25"
  }
}
```

**情况 C：只提供 start**

```text
/items/?start=2026-10-01
```

会返回 HTTP 422。

原因是：既然用户提供了部分日期模型字段，FastAPI 就需要验证整个 `DateRange` 模型，而 `end` 是没有默认值的必填字段。

### 6. 为什么这和普通可选字段不一样？

看：

```python
class DateRange(BaseModel):
    start: date
    end: date
```

模型内部两个字段都是必填。

但是：

```python
date_range: Annotated[
    DateRange | None,
    Query()
] = None
```

表示的是：**整组参数可以完全不出现。**

所以最终规则是：

| start | end | 结果 |
|---|---|---|
| 不传 | 不传 | ✅ date_range 为 None |
| 提供 | 提供 | ✅ 创建 DateRange 实例 |
| 提供 | 不传 | ❌ 422 |
| 不传 | 提供 | ❌ 422 |

注意，它只验证日期是不是合法以及必填字段是否齐全，不会自动验证：

```text
start <= end
```

这种跨字段的业务规则，需要另外增加验证逻辑。

### 🤖 Agent 开发中的作用

这特别适合以下场景：

查询 Agent 在某一时间范围内的：

- 任务执行历史。
- 工具调用日志。
- 对话记录。
- 资源消耗数据。

例如：

```text
GET /agent-logs/?start=2026-10-01&end=2026-10-25
```

而不需要日期筛选时：

```text
GET /agent-logs/
```

就可以查询默认范围的记录。

这说明 Pydantic 模型不仅能帮助你组织“一个字段”，还能帮助你管理**一组相关字段是否同时参与查询**。

## 九、综合实战：把查询参数模型真正用于 Agent 后端 🤖

这是本章最重要的动手部分。

这次我们把你之前学过的知识全部串联起来，构建一个**具备 Agent 列表查询和模拟 Agent 对话能力的 FastAPI 服务**。

### 1. 最终要实现哪些功能？

我们设计两个 API：

| API | 功能 | 主要学习内容 |
|---|---|---|
| `GET /agents/` | 查询、筛选、排序 Agent | Query 参数模型 |
| `POST /agents/{agent_id}/chat` | 向某个 Agent 提交任务 | Path + Query + Body |

注意，这两个 API 的职责不同。

`GET /agents/` 负责让用户**找到适合的 Agent**。

`POST /agents/{agent_id}/chat` 负责**使用选中的 Agent 处理任务**。

未来接入 LangGraph 或真实 LLM 时，我们主要替换第二个接口内部的模拟 Agent 逻辑即可。

### 2. 创建项目文件

在你之前的 FastAPI 学习目录中，新建：

```text
agent_query_models.py
```

建议确认当前 Python 环境和 FastAPI 版本：

```bash
python --version
python -c "import fastapi; print(fastapi.__version__)"
```

如果 FastAPI 版本低于 `0.115.0`，请在当前虚拟环境中更新：

```bash
python -m pip install -U "fastapi[standard]"
```

### 3. 完整可运行代码

```python
from typing import Annotated, Literal

from fastapi import FastAPI, Query, Path, HTTPException
from pydantic import BaseModel, Field


app = FastAPI(title="My Agent Backend")


# ========== 1. 模拟 Agent 数据库 ==========

AGENTS = [
    {
        "id": 1,
        "name": "Chat Agent",
        "tags": ["chat", "general"],
        "created_at": "2026-09-01",
        "updated_at": "2026-10-21"
    },
    {
        "id": 2,
        "name": "Code Agent",
        "tags": ["code", "python"],
        "created_at": "2026-09-10",
        "updated_at": "2026-10-19"
    },
    {
        "id": 3,
        "name": "Research Agent",
        "tags": ["research", "python"],
        "created_at": "2026-10-02",
        "updated_at": "2026-10-20"
    },
    {
        "id": 4,
        "name": "Math Agent",
        "tags": ["math"],
        "created_at": "2026-10-10",
        "updated_at": "2026-10-15"
    }
]


# ========== 2. 查询参数模型 ==========

class AgentQuery(BaseModel):

    # 禁止没有声明的查询参数
    model_config = {"extra": "forbid"}

    # 每页数量
    limit: int = Field(default=2, ge=1, le=10)

    # 跳过多少条
    offset: int = Field(default=0, ge=0)

    # 排序字段
    order_by: Literal[
        "created_at",
        "updated_at"
    ] = "created_at"

    # 筛选标签
    tags: list[str] = Field(default_factory=list)


# ========== 3. 查询 Agent 列表 ==========

@app.get("/agents/")
def list_agents(
    filters: Annotated[AgentQuery, Query()]
):

    # 获取全部 Agent
    results = AGENTS

    # 根据标签筛选
    if filters.tags:
        results = [
            agent for agent in results
            if any(
                tag in agent["tags"]
                for tag in filters.tags
            )
        ]

    # 根据指定字段排序（较新日期优先）
    results = sorted(
        results,
        key=lambda agent: agent[filters.order_by],
        reverse=True
    )

    # 记录筛选后的总数
    total = len(results)

    # 分页
    results = results[
        filters.offset:
        filters.offset + filters.limit
    ]

    return {
        "total": total,
        "items": results,
        "applied_filters": filters.model_dump()
    }


# ========== 4. Agent 对话请求体 ==========

class ChatRequest(BaseModel):

    message: str = Field(
        min_length=1,
        max_length=2000
    )

    session_id: str | None = None


# ========== 5. Agent 对话响应模型 ==========

class ChatResponse(BaseModel):

    agent_id: int
    answer: str
    steps: list[str]
    session_id: str | None = None


# ========== 6. 模拟 Agent ==========

def run_mock_agent(
    message: str,
    max_steps: int
):
    planned_steps = [
        "分析用户问题",
        "制定处理计划",
        "执行模拟工具",
        "整理信息",
        "生成回答"
    ]

    steps = planned_steps[:max_steps]

    answer = f"模拟 Agent 收到了：{message}"

    return answer, steps


# ========== 7. Agent 对话接口 ==========

@app.post(
    "/agents/{agent_id}/chat",
    response_model=ChatResponse
)
def chat(
    agent_id: Annotated[int, Path(ge=1)],
    request: ChatRequest,
    max_steps: Annotated[
        int,
        Query(ge=1, le=5)
    ] = 3
):

    # 先检查 Agent 是否存在
    agent = next(
        (a for a in AGENTS if a["id"] == agent_id),
        None
    )

    if agent is None:
        raise HTTPException(
            status_code=404,
            detail="Agent not found"
        )

    # 调用模拟 Agent
    answer, steps = run_mock_agent(
        message=request.message,
        max_steps=max_steps
    )

    # 返回规范化响应
    return ChatResponse(
        agent_id=agent_id,
        answer=answer,
        steps=steps,
        session_id=request.session_id
    )
```

### 4. 先理解第一部分：查询 Agent

我们来看：

```python

def list_agents(
    filters: Annotated[AgentQuery, Query()]
):
```

假设访问：

```text

```

FastAPI 首先创建：

```python
filters = AgentQuery(
    limit=2,
    offset=0,
    order_by="created_at",
    tags=["python"]
)
```

然后执行：

```python
if filters.tags:
```

因为 `tags` 不是空列表，条件成立。

```python

    agent for agent in results
    if any(
        tag in agent["tags"]
        for tag in filters.tags

]
```

这是一段 Python 列表推导式。

用普通语言解释就是：

> 遍历所有 Agent，只保留包含任意指定标签的 Agent。

于是剩下：

```text

Research Agent
```

再经过：

```python
sorted(...)
```

按照创建时间从新到旧排序。

最后通过：

```python
    filters.offset:
    filters.offset + filters.limit

```

这里日期使用统一的 `YYYY-MM-DD` 字符串，所以示例中可以按字符串排序；真实项目更适合使用数据库日期类型以及对应的排序操作。

### 5. 再理解第二部分：用户真正调用 Agent

这里的函数：

## 十、这章知识如何与未来真正的 Agent 项目串联？

现在我们将本章放到更大的系统中理解。

你可以想象以后开发的是一个支持多个 Agent 的平台：

选择 Agent，输入任务

GET /agents/

        **Agent 对话接口**
        
POST /agents/2/chat

ChatRequest 模型

接收用户任务

    

  

  

    **业务与数据服务**
    
读取 Agent 定义、用户权限、历史记录

  

  

    **Agent 执行层**

      

          
          
LLM

    **FastAPI 返回结构化结果**
    
ChatResponse / JSON / 后续可以升级为流式输出

### 这几章知识分别负责什么？

| 知识 | 未来 Agent 项目中的作用 |
|---|---|
| 路径参数 | 指定哪个 Agent、会话或任务 |
| 查询参数 | 控制查询、筛选、分页 |
| 请求体 | 接收用户任务和结构化输入 |
| Query + 字符串校验 | 检查搜索关键词等输入 |
| Path + 数值校验 | 限制资源 ID 的格式与数值 |
| 查询参数模型 | 集中管理一组查询条件 |
| Field | 定义模型字段的校验规则 |
| Literal | 限制排序字段、状态等固定选项 |
| response_model | 规范接口返回结构 |

这里还需要理解一个架构上的区别。

**AgentQuery 和 AgentRunConfig 不是同一种东西。**

例如：

```python
class AgentQuery(BaseModel):
    limit: int = 10
    offset: int = 0
```

它负责查询 Agent 列表。

而：

```python
class AgentRunConfig(BaseModel):
    max_steps: int = Field(3, ge=1, le=5)
    temperature: float = Field(0.7, ge=0, le=1)
```

它描述的是 Agent 的运行配置。

后者通常更适合放进 Agent 调用的请求体中，并且需要真正传递给 Agent 执行器和模型服务才能生效。

同样是 Pydantic 模型，**具体扮演什么角色，由业务需求以及 FastAPI 的参数声明方式决定。**

这也是为什么我们不能简单地把“查询参数模型”等同于“Agent 的模型配置”。

# 📘 FastAPI 查询参数模型：零基础完整讲解

FastAPI 系列教程 · 第 6 章 · 从入门到 Agent 后端开发

今天我们学习 FastAPI 官方教程的 **《查询参数模型》（Query Parameter Models）**。

官方教程入口：

- <Link url={turn184746view0.url.uri} title="FastAPI 官方中文教程：查询参数模型"/>
- <Link url={turn184746view1.url.uri} title="FastAPI 官方英文教程：Query Parameter Models"/>

这一章的核心知识只有一句话：

**当一个 API 有很多相关的查询参数时，可以使用 Pydantic 的 BaseModel，把这些参数集中管理，而不必全部写在函数参数列表中。**

你之前学到的 `Annotated`、`Query()`、`Field()`、`BaseModel`，将在这一章真正组合起来。

## 一、先理解：为什么需要查询参数模型？

### 1. 回顾上一章的代码

假设你正在开发一个 Agent 管理平台，可以查询 Agent 列表。

用户能够设置：

- `limit`：最多返回多少个 Agent。
- `offset`：跳过前面多少个 Agent。
- `order_by`：按照什么字段排序。
- `tags`：按照哪些标签筛选。

你以前可能会这样写：

```python
from typing import Annotated
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/agents/")
def get_agents(
    limit: Annotated[int, Query(gt=0, le=100)] = 10,
    offset: Annotated[int, Query(ge=0)] = 0,
    order_by: str = "created_at",
    tags: Annotated[list[str] | None, Query()] = None
):
    return {
        "limit": limit,
        "offset": offset,
        "order_by": order_by,
        "tags": tags
    }
```

这段代码没有问题。

访问：

```text
/agents/?limit=5&offset=10&order_by=created_at&tags=python
```

FastAPI 可以正确读取参数。

但是，你有没有发现：**函数参数列表开始变长了。**

如果未来 Agent 平台还需要：

```text
model
temperature
max_steps
timeout
search
status
sort_order
```

你的函数可能就会有十几个甚至更多参数。

这会带来三个问题：

1. **代码不容易阅读**：业务逻辑之前堆满了参数声明。
2. **重复代码较多**：多个接口都需要分页、排序时，需要反复定义。
3. **维护成本增加**：修改一个参数的规则，可能需要修改多个接口。

### 2. 查询参数模型就是为了解决这些问题

我们可以把多个参数放进一个 Pydantic 模型中：

```python
from pydantic import BaseModel, Field

class AgentFilter(BaseModel):
    limit: int = Field(10, gt=0, le=100)
    offset: int = Field(0, ge=0)
    order_by: str = "created_at"
    tags: list[str] = Field(default_factory=list)
```

然后在 FastAPI 接口中写：

```python
@app.get("/agents/")
def get_agents(
    filters: Annotated[AgentFilter, Query()]
):
    return filters
```

是不是简洁了很多？

  
查询参数模型的核心思想

    **用户访问 API**
    
`?limit=5&offset=10&order_by=created_at`

  

  

      **FastAPI + Query()**
      
从 URL 中提取参数

    

> *省略对话原版动态控件。*

  

  

    **Pydantic 创建 AgentFilter 对象**
    
解析类型、检查数值、应用默认值

  

  

    **业务函数接收 `filters`**
    
使用 filters.limit、filters.offset 等属性

你可以把查询参数模型理解成一个**专门收集和检查一组查询条件的容器**。

### 🤖 在未来 Agent 开发中有什么用？

以后你可能有两个不同的接口：

```text
GET /agents
GET /tasks
```

一个查询 Agent，另一个查询 Agent 执行任务。

但两者都可能需要：

```text
limit=10
offset=0
```

这时你可以让它们复用同一个 `PaginationParams` 模型，不必为每个接口重复写分页参数。

进一步，你还可以定义：

- `AgentFilter`：管理 Agent 搜索条件。
- `TaskFilter`：管理任务状态、时间范围。
- `AgentRunConfig`：管理允许客户端设置的 Agent 执行配置。

**本章最重要的价值不是减少几行代码，而是让 API 的参数管理更加清晰、可复用。**

这里也有一个版本提醒：查询参数模型从 **FastAPI 0.115.0** 开始支持。如果你的环境较旧，需要升级。

可以在你之前使用的 `(llm)` 环境中检查：

```bash
python -c "import fastapi; print(fastapi.__version__)"
```

## 二、官方示例：使用 Pydantic 模型声明查询参数

现在进入官方教程第一节「使用 Pydantic 模型的查询参数」。

### 1. 官方完整示例

```python
from typing import Annotated, Literal

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()


class FilterParams(BaseModel):
    limit: int = Field(100, gt=0, le=100)
    offset: int = Field(0, ge=0)
    order_by: Literal["created_at", "updated_at"] = "created_at"
    tags: list[str] = []


@app.get("/items/")
async def read_items(
    filter_query: Annotated[FilterParams, Query()]
):
    return filter_query
```

看起来有点复杂，但其实这段代码只做了两件事：

**第一：使用 `FilterParams` 描述查询参数的结构与规则。**

**第二：使用 `Query()` 告诉 FastAPI，这个模型里的字段要从 URL 的查询参数中获取。**

我们逐行解释。

### 2. `from typing import Annotated, Literal`

你已经学过：

```python
Annotated
```

它可以将类型与 FastAPI 的参数元数据组合起来。

这一章新增的是：

```python
Literal
```

`Literal` 也是 Python 标准库 `typing` 中的工具。

它的作用是：**让一个字段只能使用预先规定的几个值。**

例如：

```python
from typing import Literal

order_by: Literal["created_at", "updated_at"]
```

表示 `order_by` 只能是：

```text
created_at
updated_at
```

不能是：

```text
name
price
hello
```

你可能会觉得，这不就是上一章之前学习的 `Enum` 吗？

没错，它们有相似用途。

| 对比 | Literal | Enum |
|---|---|---|
| 约束固定选项 | ✅ | ✅ |
| 需要额外定义类 | 不需要 | 需要 |
| 适用场景 | 少数简单固定值 | 多处复用、需要独立枚举类型 |
| 例子 | `Literal["asc", "desc"]` | `SortOrder.asc` |

在你目前这个阶段，可以这样理解：

**只有几个简单选项时，使用 Literal 往往很方便；复杂或多处复用的选项集合，可以考虑 Enum。**

### 3. `class FilterParams(BaseModel)`

```python
class FilterParams(BaseModel):
```

这句话你已经非常熟悉了。

我们之前写过：

```python
class ChatRequest(BaseModel):
    message: str
```

两者都使用 Pydantic 模型，但用途不同。

| 模型 | 用途 | 数据来源 |
|---|---|---|
| `ChatRequest` | 描述聊天请求体 | JSON Body |
| `FilterParams` | 描述查询条件 | URL Query |

**BaseModel 本身不决定参数一定来自请求体。**

真正的区别，在于 FastAPI 接口中如何声明这个模型。

例如：

```python
request: ChatRequest
```

通常将模型作为请求体参数。

而：

```python
filter_query: Annotated[FilterParams, Query()]
```

则明确告诉 FastAPI：从查询字符串中提取 `FilterParams` 的字段。

这是本章最应该掌握的区别。

## 三、逐行拆解 FilterParams：四种字段写法

### 1. `limit: int = Field(100, gt=0, le=100)`

先看：

```python
limit: int = Field(100, gt=0, le=100)
```

这行代码表达了三个要求：

| 代码 | 含义 |
|---|---|
| `limit: int` | limit 必须是整数 |
| `Field(100)` | 默认值为 100 |
| `gt=0` | 必须大于 0 |
| `le=100` | 必须小于或等于 100 |

组合起来就是：

\[
0 < \text{limit} \leq 100
\]

例如：

| 输入 | 结果 | 原因 |
|---|---|---|
| 不传 limit | ✅ | 使用默认值 100 |
| `limit=1` | ✅ | 满足范围 |
| `limit=50` | ✅ | 满足范围 |
| `limit=0` | ❌ 422 | 不满足 gt=0 |
| `limit=101` | ❌ 422 | 不满足 le=100 |
| `limit=hello` | ❌ 422 | 无法解析为整数 |

这里还有一个语法细节。

```python
Field(100, gt=0, le=100)
```

等价于：

```python
Field(default=100, gt=0, le=100)
```

第一个位置参数 `100` 就是默认值。

你以后阅读不同项目代码时，会经常遇到这两种写法。

### 2. `offset: int = Field(0, ge=0)`

```python
offset: int = Field(0, ge=0)
```

表示：

- 必须是整数。
- 默认值为 0。
- 必须大于或等于 0。

那 `offset` 到底是什么？

假设 Agent 数据库中有 5 个 Agent：

```python
agents = [
    "Chat Agent",
    "Code Agent",
    "Research Agent",
    "Math Agent",
    "Travel Agent"
]
```

如果：

```python
offset = 2
limit = 2
```

我们可以写：

```python
agents[offset:offset + limit]
```

也就是：

```python
agents[2:4]
```

返回：

```python
["Research Agent", "Math Agent"]
```

所以：

- `offset`：跳过多少条。
- `limit`：最多取多少条。

这和你之前学习过的 `skip` 完全类似，只是命名不同。

### 3. `order_by: Literal[...] = "created_at"`

官方代码：

```python
order_by: Literal["created_at", "updated_at"] = "created_at"
```

这里有两个不同的概念。

**第一个：允许的取值**

```python
Literal["created_at", "updated_at"]
```

只允许两个值。

**第二个：默认值**

```python
= "created_at"
```

用户没有传入 `order_by` 时，使用 `"created_at"`。

例如：

```text
/items/?order_by=updated_at
```

合法。

```text
/items/?order_by=name
```

不合法，会返回 422。

但是一定要注意：

**Literal 只负责验证用户选择的排序字段，不能自动让数据库完成排序。**

真正的排序逻辑仍然需要你自己编写。

例如：

```python
sorted(items, key=lambda item: item["created_at"])
```

这才是执行排序的 Python 业务逻辑。

在 Agent 项目中也是一样：

```python
order_by: Literal["created_at", "updated_at"]
```

只是规定用户允许选择哪些排序字段。

### 4. `tags: list[str] = []`

官方代码：

```python
tags: list[str] = []
```

这里：

```python
list[str]
```

表示字符串列表。

```python
= []
```

表示默认值为空列表。

例如用户访问：

```text
/items/?tags=python&tags=fastapi
```

FastAPI 会得到：

```python
tags = ["python", "fastapi"]
```

如果用户不传 tags，则默认：

```python
tags = []
```

之前你学过的列表查询参数，在这一章仍然适用。

**一个代码习惯上的补充：**

Pydantic v2 会妥善处理这里的可变默认列表，但我更建议你在实际项目中写：

```python
tags: list[str] = Field(default_factory=list)
```

`default_factory=list` 的意思是：需要默认值时创建一个新的空列表。

这种写法更明确，也有助于你建立良好的 Python 可变对象使用习惯。

### 5. 四个字段综合起来

官方模型：

```python
class FilterParams(BaseModel):
    limit: int = Field(100, gt=0, le=100)
    offset: int = Field(0, ge=0)
    order_by: Literal["created_at", "updated_at"] = "created_at"
    tags: list[str] = []
```

可以理解成一张查询配置表：

| 字段 | Python 类型 | 默认值 | 校验规则 |
|---|---|---|---|
| limit | int | 100 | 1～100 |
| offset | int | 0 | 不小于 0 |
| order_by | Literal | created_at | 只能选择两个字段 |
| tags | list[str] | [] | 字符串列表 |

现在，这四个参数就被统一管理起来了。

## 四、最关键的一行：`Annotated[FilterParams, Query()]`

现在来看接口：

```python
@app.get("/items/")
async def read_items(
    filter_query: Annotated[FilterParams, Query()]
):
    return filter_query
```

**这一行就是本章最重要的代码：**

```python
filter_query: Annotated[FilterParams, Query()]
```

我们一层一层拆开。

### 第一层：`filter_query`

这是 Python 函数参数名。

它只是一个变量名，你也可以叫：

```python
filters
```

或者：

```python
params
```

只要使用方式正确，名称可以自己决定。

### 第二层：`FilterParams`

```python
filter_query: FilterParams
```

表示：

> 进入函数时，我希望 filter_query 是一个 FilterParams 类型的对象。

也就是说，它应该具有：

```python
filter_query.limit
filter_query.offset
filter_query.order_by
filter_query.tags
```

这些属性。

### 第三层：`Query()`

```python
Annotated[FilterParams, Query()]
```

明确告诉 FastAPI：

> 请从 URL 查询参数中提取数据，再按照 FilterParams 模型解析和校验。

例如用户访问：

```text
/items/?limit=5&offset=2&order_by=updated_at&tags=python&tags=fastapi
```

FastAPI 会自动完成类似下面的工作：

```python
filter_query = FilterParams(
    limit=5,
    offset=2,
    order_by="updated_at",
    tags=["python", "fastapi"]
)
```

注意：这是为了理解而展示的等效过程，你不需要自己在路由函数中创建这个对象。

然后你可以通过：

```python
filter_query.limit
```

得到：

```python
5
```

通过：

```python
filter_query.tags
```

得到：

```python
["python", "fastapi"]
```

### 为什么不需要把参数写成 `filter_query.limit`？

这是初学者特别容易困惑的地方。

例如，你不需要发送：

```text
/items/?filter_query.limit=5
```

更不需要在 URL 中提交 JSON 字符串来代替这些普通字段。

正确写法仍然是：

```text
/items/?limit=5&offset=2
```

**查询参数模型只是 Python 后端内部组织数据的方式，不会自动改变 URL 查询参数的扁平结构。**

FastAPI 会根据模型中的字段名称，找到对应的 URL 参数。

### 还记得 `.model_dump()` 吗？

上一章《请求体》中我们已经学习：

```python
item.model_dump()
```

现在查询参数模型也可以使用它。

例如：

```python
@app.get("/items/")
def read_items(
    filter_query: Annotated[FilterParams, Query()]
):
    return filter_query.model_dump()
```

假设用户访问：

```text
/items/?limit=5&tags=python
```

返回：

```json
{
  "limit": 5,
  "offset": 0,
  "order_by": "created_at",
  "tags": ["python"]
}
```

这里未提供的 `offset` 和 `order_by` 使用了默认值。

你已经可以发现：

**请求体模型和查询参数模型都是 Pydantic 对象，主要区别是它们的数据来自 HTTP 请求的哪个位置。**

## 六、禁止额外的查询参数：`extra="forbid"`

这部分是官方教程的第三个核心知识点。

### 1. 先思考一个问题

我们已经定义了：

```python
class FilterParams(BaseModel):
    limit: int = 100
    offset: int = 0
```

说明这个接口设计了两个查询字段：

```text
limit
offset
```

但是如果用户访问：

```text
/items/?limit=10&offset=0&unknown=hello
```

会怎样？

这里出现了一个你没有定义的参数：

```text
unknown=hello
```

默认情况下，Pydantic 模型通常会忽略多余的字段。

也就是说，接口可能正常执行，但 `unknown` 不会被放进最终的模型数据中。

有时候，我们不希望出现这种情况。

例如用户把：

```text
temperature
```

误写成：

```text
temprature
```

如果静默忽略这个参数，用户可能以为自己已经修改了模型采样配置，实际上根本没有生效。

所以我们希望：**遇到不认识的字段，就直接报错。**

### 2. 官方使用 `model_config`

```python
from pydantic import BaseModel

class FilterParams(BaseModel):
    model_config = {"extra": "forbid"}

    limit: int = 100
    offset: int = 0
```

这行是本节重点：

```python
model_config = {"extra": "forbid"}
```

拆开理解：

| 代码 | 含义 |
|---|---|
| `model_config` | Pydantic 模型配置 |
| `extra` | 额外出现的字段 |
| `forbid` | 禁止 |

组合起来就是：

> 除了模型明确定义的字段，不接受额外字段。

### 3. 测试不同请求

| 请求 | 结果 |
|---|---|
| `/items/?limit=10` | ✅ 200 |
| `/items/?offset=5` | ✅ 200 |
| `/items/?limit=10&offset=5` | ✅ 200 |
| `/items/?limit=10&unknown=hello` | ❌ 422 |

如果用户传入：

```text
/items/?limit=10&tool=plumbus
```

FastAPI 会返回类似：

```json
{
  "detail": [
    {
      "type": "extra_forbidden",
      "loc": ["query", "tool"],
      "msg": "Extra inputs are not permitted",
      "input": "plumbus"
    }
  ]
}
```

这里：

```json
"loc": ["query", "tool"]
```

告诉你：问题出现在查询参数 `tool` 上。

而：

```json
"type": "extra_forbidden"
```

表示传入了不允许的额外字段。

### 4. 为什么对 Agent 开发很有帮助？

假设你开发：

```text
POST /agents/1/chat?max_steps=3
```

用户却写成：

```text
POST /agents/1/chat?max_step=3
```

少了一个字母 `s`。

如果没有额外参数校验，服务可能直接使用默认的 `max_steps`，用户自己却不知道参数名称写错了。

如果使用：

```python
model_config = {"extra": "forbid"}
```

就可以让这种错误更早暴露。

这是我建议你在学习 Agent API 的参数配置时练习的一个选项。

不过它并不代表所有生产接口都必须禁止额外参数。严格验证更容易发现错误，但也会影响与旧客户端或其他参数的兼容性，实际项目要根据需求选择。

## 七、进阶：多个查询参数模型能不能组合使用？

这里补充官方英文教程新增的内容。

中文教程目前主要介绍单个模型与额外字段校验；英文教程还提供了**组合多个模型**、**可选模型**的示例。

这两项属于较新的 FastAPI 功能：

- 组合查询参数模型：从 FastAPI **0.157.0** 开始支持。
- 可选查询参数模型：从 FastAPI **0.159.0** 开始支持。

如果你的版本较旧，下面的进阶代码可能无法运行。版本要求来自 FastAPI 官方更新记录。

### 1. 为什么需要组合多个模型？

假设你有两类查询参数。

第一类管理分页：

```python
class Pagination(BaseModel):
    limit: int = Field(10, ge=1)
    offset: int = Field(0, ge=0)
```

第二类管理筛选：

```python
class Filters(BaseModel):
    tags: list[str] = Field(default_factory=list)
```

你希望一个接口同时使用它们。

可以这样写：

```python
from typing import Annotated

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()


class Pagination(BaseModel):
    limit: int = Field(10, ge=1)
    offset: int = Field(0, ge=0)


class Filters(BaseModel):
    tags: list[str] = Field(default_factory=list)


@app.get("/items/")
def read_items(
    pagination: Annotated[Pagination, Query()],
    filters: Annotated[Filters, Query()],
    search: str | None = None
):
    return {
        "pagination": pagination,
        "filters": filters,
        "search": search
    }
```

这里有两个独立的模型对象：

```python
pagination
filters
```

以及一个普通的查询参数：

```python
search
```

例如访问：

```text
/items/?limit=5&offset=10&tags=python&tags=agent&search=FastAPI
```

可以得到类似结果：

```json
{
  "pagination": {
    "limit": 5,
    "offset": 10
  },
  "filters": {
    "tags": ["python", "agent"]
  },
  "search": "FastAPI"
}
```

注意，URL 中的查询参数仍然是扁平的。

你不需要写成：

```text
?pagination.limit=5&filters.tags=python
```

### 2. 为什么拆成 Pagination 和 Filters？

因为它们负责不同的事情。

  

    **GET /items/**
    
一个请求，包含多种查询条件

  

  

      

        **Pagination**
        
limit、offset

分页规则

    

      

        **Filters**
        
tags

筛选规则

    

  

  

    **业务逻辑**
    
先筛选数据，再根据分页设置返回结果

这样以后你开发：

```text
GET /agents
GET /tasks
GET /sessions
```

不同接口都可以复用 `Pagination`，而筛选模型则可以根据业务不同而变化。

不过，需要注意两点：

- 不同模型尽量不要声明同名但含义不同的查询参数。
- 从 FastAPI 0.160.0 起，模型的 `extra="forbid"` 也会检查同一请求中其他模型或独立查询参数提供的字段。组合模型时不能随意给每个模型都设置 `extra="forbid"`，否则可能互相拒绝对方的字段。

对于你目前的学习阶段，我建议先掌握单个查询参数模型，再把多模型组合当作工程化进阶知识。

## 八、进阶：整个查询参数模型也可以是可选的吗？

可以，在支持该功能的较新版本 FastAPI 中，我们可以写：

```python
from datetime import date
from typing import Annotated

from fastapi import FastAPI, Query
from pydantic import BaseModel

app = FastAPI()


class DateRange(BaseModel):
    start: date
    end: date


@app.get("/tasks/")
def get_tasks(
    limit: int = 10,
    date_range: Annotated[
        DateRange | None,
        Query()
    ] = None
):
    return {
        "limit": limit,
        "date_range": date_range
    }
```

这一节先理解两个知识点。

### 1. `date` 是什么？

```python
from datetime import date
```

`date` 是 Python 日期类型。

FastAPI 可以解析类似：

```text
2026-10-01
```

这种日期格式。

### 2. `DateRange | None = None` 是什么意思？

```python
date_range: Annotated[
    DateRange | None,
    Query()
] = None
```

表示：

> 整组日期查询条件可以不提供。

例如：

```text
/tasks/
```

没有日期参数，使用：

```python
date_range = None
```

但如果用户想按日期区间查询，就可以传入：

```text
/tasks/?start=2026-10-01&end=2026-10-20
```

FastAPI 会将它们解析为 `DateRange` 对象。

如果只提供 `start`，但没有 `end`，由于 `DateRange` 定义了两个必填字段，通常会返回 422。

这里还有一个重要区别：**日期格式合法，并不自动保证 start 早于或等于 end。** 这种跨字段的业务规则还需要另外编写验证逻辑。

### 🤖 在 Agent 项目中的实际作用

假设你以后开发一个可以查看历史执行记录的 Agent 平台：

```text
GET /tasks?start=2026-10-01&end=2026-10-20
```

日期模型可以集中管理任务记录的时间过滤条件。

如果用户不指定时间范围，就查询默认范围；如果提供日期，就按照日期筛选。

注意，这里的示例只是返回查询参数，还没有连接数据库查询历史任务。

**这一节是新版本功能，初学阶段不需要强行使用。** 你现在完全可以先用普通的独立查询参数实现相同的业务需求。

## 九、综合实战：为 Agent 系统建立真正可复用的查询参数模型 🤖

现在来到本章最重要的实践部分。

之前我们完成过：

- 使用 Path 选择 Agent。
- 使用 Query 设置 `max_steps`。
- 使用 BaseModel 接收用户问题。
- 使用 Field 校验消息长度。
- 使用 HTTPException 处理不存在的 Agent。

这一次，我们要把这些功能全部连接起来，再增加 **查询参数模型**。

### 1. 这次项目要实现哪些功能？

  

    **个人 Agent 管理平台**

  

    **接口一：查询 Agent 列表**
    
`GET /agents/`

支持关键词搜索、标签筛选、分页和排序。

  

    **接口二：调用指定 Agent**
    
`POST /agents/{`agent_id`}/chat`

接收用户问题，根据运行配置执行模拟 Agent。

我们要设计四个 Pydantic 模型：

| 模型名称 | 负责什么 | 在 Agent 中的作用 |
|---|---|---|
| `AgentFilter` | 查询参数模型 | 搜索、分页、筛选 Agent |
| `RunOptions` | 查询参数模型 | 设置 Agent 允许的执行步骤数等 |
| `ChatRequest` | 请求体模型 | 获取用户的问题和会话 ID |
| `ChatResponse` | 响应模型 | 规范 Agent 的返回结果 |

这里你会第一次感受到：

**Pydantic 模型不是只能用来接收用户的问题。它还能为 Agent 的不同功能建立清晰的数据契约。**

### 2. 创建文件

在你的 FastAPI 学习目录中新建：

```text
agent_query_models.py
```

### 3. 完整可运行代码

下面使用单个文件，方便你学习。真实项目成熟后，可以再把模型、路由和 Agent 业务逻辑拆分到不同文件中。

```python
from typing import Annotated, Literal

from fastapi import FastAPI, Path, Query, HTTPException
from pydantic import BaseModel, Field


app = FastAPI(title="My Agent API - Query Models")


# ========== 一、模拟 Agent 数据库 ==========

AGENTS = [
    {
        "id": 1,
        "name": "Chat Agent",
        "tags": ["chat", "general"]
    },
    {
        "id": 2,
        "name": "Code Agent",
        "tags": ["code", "python"]
    },
    {
        "id": 3,
        "name": "Research Agent",
        "tags": ["research", "python"]
    }
]


# ========== 二、Agent 列表的查询参数模型 ==========

class AgentFilter(BaseModel):
    model_config = {"extra": "forbid"}

    keyword: str | None = Field(
        default=None,
        min_length=2,
        max_length=30
    )

    limit: int = Field(
        default=10,
        ge=1,
        le=50
    )

    offset: int = Field(
        default=0,
        ge=0
    )

    order_by: Literal["id", "name"] = "id"

    tags: list[str] = Field(default_factory=list)


# ========== 三、Agent 运行配置模型 ==========

class RunOptions(BaseModel):
    model_config = {"extra": "forbid"}

    max_steps: int = Field(
        default=3,
        ge=1,
        le=5
    )

    verbose: bool = False


# ========== 四、Agent 请求体模型 ==========

class ChatRequest(BaseModel):
    message: str = Field(
        min_length=1,
        max_length=2000
    )

    session_id: str | None = None


# ========== 五、Agent 响应模型 ==========

class ChatResponse(BaseModel):
    agent_id: int
    answer: str
    steps: list[str]
    session_id: str | None = None
    options: RunOptions


# ========== 六、查询 Agent 列表 ==========

@app.get("/agents/")
def list_agents(
    filters: Annotated[AgentFilter, Query()]
):
    found = AGENTS

    # 1. 按关键词搜索
    if filters.keyword is not None:
        found = [
            agent for agent in found
            if filters.keyword.lower()
            in agent["name"].lower()
        ]

    # 2. 按标签筛选
    if filters.tags:
        found = [
            agent for agent in found
            if any(
                tag in agent["tags"]
                for tag in filters.tags
            )
        ]

    # 3. 排序
    found = sorted(
        found,
        key=lambda agent: agent[filters.order_by]
    )

    # 4. 记录筛选后的总数
    total = len(found)

    # 5. 分页
    page = found[
        filters.offset:filters.offset + filters.limit
    ]

    return {
        "total": total,
        "items": page,
        "filters": filters.model_dump()
    }


# ========== 七、调用指定 Agent ==========

@app.post(
    "/agents/{agent_id}/chat",
    response_model=ChatResponse
)
def chat(
    agent_id: Annotated[int, Path(ge=1)],
    request: ChatRequest,
    options: Annotated[RunOptions, Query()]
):
    # 1. 查找指定 Agent
    agent = next(
        (a for a in AGENTS if a["id"] == agent_id),
        None
    )

    if agent is None:
        raise HTTPException(
            status_code=404,
            detail="Agent not found"
        )

    # 2. 模拟 Agent 执行
    planned_steps = [
        "理解任务",
        "制定计划",
        "调用模拟工具",
        "整理信息",
        "输出回答"
    ]

    steps = planned_steps[:options.max_steps]

    # 3. 生成模拟回答
    answer = (
        f"{agent['name']} 收到了：{request.message}"
    )

    # 4. 按运行配置控制详细程度
    if options.verbose:
        answer += f"（模拟执行 {len(steps)} 步）"

    # 5. 返回标准响应
    return ChatResponse(
        agent_id=agent_id,
        answer=answer,
        steps=steps,
        session_id=request.session_id,
        options=options
    )
```

### 4. 代码中的知识怎样串联起来？

重点看第二个接口：

```python
@app.post(
    "/agents/{agent_id}/chat",
    response_model=ChatResponse
)
def chat(
    agent_id: Annotated[int, Path(ge=1)],
    request: ChatRequest,
    options: Annotated[RunOptions, Query()]
):
```

这几行代码几乎把前面六章的核心知识全部用到了。

  
一次 Agent 请求如何经过 FastAPI

    **POST /agents/2/chat?max_steps=2&verbose=true**
    
Body: {"message": "你好"}

  

  

      
      **Path：解析 agent_id**

    
得到整数 `agent_id = 2`，检查是否大于或等于 1。

  

  

      
      **Query + RunOptions：解析运行参数**

    
得到 `max_steps = 2`、`verbose = True`。

  

  

      
      **Body + ChatRequest：解析用户问题**

    
得到 `request.message = "你好"`。

  

  

      
      **业务逻辑：查找并执行 Agent**

    
查询 Agent 2，模拟执行 2 个步骤。

  

  

    **ChatResponse：规范返回内容**
    
输出 agent_id、answer、steps、options 等字段

这就是你一直希望理解的 **FastAPI 与 Agent 开发之间的完整连接关系**。

### 5. 为什么这个项目要定义四个模型？

我们逐个对应。

**`AgentFilter`：负责查询 Agent。**

```python
filters: Annotated[AgentFilter, Query()]
```

未来可以和数据库、Agent 列表、任务检索结合。

**`RunOptions`：负责 Agent 的运行参数。**

```python
options: Annotated[RunOptions, Query()]
```

未来可以把 `max_steps`、模型选择、超时等允许客户端控制的配置传递给 Agent 执行器。

**`ChatRequest`：负责用户输入。**

```python
request: ChatRequest
```

未来可以包含消息、会话 ID 和其他对话数据。

**`ChatResponse`：负责输出结构。**

```python
response_model=ChatResponse
```

未来可以返回 Agent 回答、任务状态或其他明确规定的字段。

你可以记住一个重要设计思想：

**不同类型的数据，使用不同职责的模型。**

比如用户的问题、Agent 的运行配置以及搜索筛选条件，不一定要全部塞进一个巨大的 `BaseModel` 里。

### 6. `max_steps` 到底是怎样生效的？

这一次，我们没有只验证它，而是真的在模拟 Agent 中使用了它。

```python
steps = planned_steps[:options.max_steps]
```

假设：

```python
options.max_steps = 2
```

它就取前两个步骤：

```python
[
    "理解任务",
    "制定计划"
]
```

所以这一次：

- `Field(ge=1, le=5)` 负责验证范围。
- `Query()` 负责从 URL 提取参数。
- `RunOptions` 负责组织参数。
- `options.max_steps` 负责把配置交给业务逻辑。
- Python 列表切片负责执行模拟步骤数限制。

但要特别说明：目前只是模拟步骤列表切片，**并没有真正运行 LLM 或 LangGraph 的工具调用循环**。以后接入真实 Agent 时，需要在执行器内部实现对应的步骤预算。

### 7. 为什么 `verbose` 也属于 RunOptions？

```python
verbose: bool = False
```

它表示是否提供更详细的回答信息。

例如：

```text
?verbose=false
```

表示使用默认的简洁回答。

```text
?verbose=true
```

表示在返回的答案中额外添加模拟步骤数。

你之前学过的布尔查询参数，经过这一章后，也可以统一放进 `RunOptions` 模型中管理。

### 4. 练习排查 HTTP 错误

| 测试情况 | 预期状态码 | 原因 |
|---|---|---|
| `GET /agents/?limit=0` | 422 | limit 小于允许的最小值 |
| `GET /agents/?order_by=price` | 422 | price 不在 Literal 选项中 |
| `GET /agents/?unknown=123` | 422 | AgentFilter 禁止额外参数 |
| `GET /agents/?keyword=a` | 422 | 搜索关键词太短 |
| `POST /agents/2/chat?max_steps=6` | 422 | 超过运行配置的最大值 |
| `POST /agents/99/chat` | 404 | Agent 不存在 |
| `POST /agents/2/chat`，message 为空 | 422 | 请求体校验失败 |

这些结果假设其他输入均有效，并使用了对应的 HTTP 方法。

## 十一、Agent 开发中必须区分的三种“模型”

到这里，我想补充一个非常重要、但官方教程并不会重点解释的概念。

你正在学习的是 Agent 开发，因此今后会经常碰到“模型”这个词。

但是不同场景中的“模型”，意思并不相同。

| 名称 | 示例 | 负责什么 |
|---|---|---|
| Pydantic 数据模型 | `AgentFilter`、`ChatRequest` | 规定输入输出数据结构 |
| LLM 大语言模型 | GPT 等 | 理解语言、生成回答 |
| Agent 执行流程 | LangGraph 等 | 组织状态、工具调用和任务步骤 |

例如：

```python
class RunOptions(BaseModel):
    max_steps: int = Field(3, ge=1, le=5)
```

这只是一个 Pydantic 数据模型，不会自己运行 Agent，也不会调用大语言模型。

但它可以成为 Agent 执行器的配置输入。

未来你可能采用这样的工程结构：

```text
my_agent_project/
├── main.py
│
├── routers/
│   ├── agents.py         # FastAPI 路由
│   └── chat.py           # 对话接口
│
├── schemas/
│   ├── filters.py        # 查询参数模型
│   ├── requests.py       # 请求体模型
│   └── responses.py      # 响应模型
│
├── agents/
│   └── assistant.py      # Agent 执行逻辑
│
├── services/
│   └── llm.py            # LLM 调用封装
│
└── database/
    └── storage.py        # 持久化存储
```

你现在学习的是其中的**接口层和数据模型层**。

后面继续学习依赖注入、数据库、异步编程等内容时，才会逐渐把其他部分补齐。

## 十三、本章最终总结

| 核心知识 | 关键代码 | 重要程度 |
|---|---|---|
| 查询参数模型 | `class FilterParams(BaseModel)` | ⭐⭐⭐ |
| 声明查询来源 | `Annotated[FilterParams, Query()]` | ⭐⭐⭐ |
| 字段默认值 | `Field(default=10)` | ⭐⭐⭐ |
| 数值校验 | `Field(ge=1, le=100)` | ⭐⭐⭐ |
| 固定选项 | `Literal["asc", "desc"]` | ⭐⭐⭐ |
| 列表查询字段 | `list[str]` | ⭐⭐⭐ |
| 创建空列表 | `Field(default_factory=list)` | ⭐⭐ |
| 读取模型属性 | `filters.limit` | ⭐⭐⭐ |
| 模型转换字典 | `filters.model_dump()` | ⭐⭐⭐ |
| 禁止额外参数 | `model_config={"extra":"forbid"}` | ⭐⭐ |
| 组合多个查询模型 | 多个 `Annotated[..., Query()]` | ⭐⭐ |
| 可选查询参数模型 | `Annotated[Model \| None, Query()] = None` | ⭐ |

### 最应该记住的三个知识点

**第一：BaseModel 定义数据结构和验证规则。**

```python
class AgentFilter(BaseModel):
    limit: int = Field(10, ge=1, le=100)
```

**第二：Query() 告诉 FastAPI 去哪里获取这些数据。**

```python
filters: Annotated[AgentFilter, Query()]
```

**第三：业务逻辑真正使用模型中已经验证的数据。**

```python
limit = filters.limit
```

这三步连接起来就是：

**定义规则 → 接收并校验参数 → 业务逻辑使用参数。**

### 四个最终思考题

希望你能在不看教程的情况下，独立解释：

1. **为什么 `FilterParams` 继承 BaseModel，却能够接收 URL 查询参数，而不一定是 JSON 请求体？**
2. **为什么使用 `model_config = {"extra": "forbid"}` 能帮助发现 Agent API 中的拼写错误？**
3. **为什么 `order_by: Literal["id", "name"]` 能检查排序选项，却不能自动完成排序？**
4. **如果未来 LangGraph Agent 需要 `max_steps`、`verbose`、`model_name` 等运行配置，应该如何使用一个 RunOptions 模型组织这些参数，并把它们真正传递给 Agent？**
