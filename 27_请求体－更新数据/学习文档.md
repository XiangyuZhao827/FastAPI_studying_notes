# 📘 FastAPI 第 21 章：请求体－更新数据（Body – Updates）

FastAPI 基础 → LLM / Agent 后端开发 · 延续之前的逐行讲解、JSON 测试、Agent 实战与章末自测

官方教程：[请求体－更新数据](https://fastapi.tiangolo.com/zh/tutorial/body-updates/)

这一章和你之前学过的《请求体》《更多模型》《响应模型》以及刚刚接触过的 `jsonable_encoder()` 联系非常紧密。

今天主要掌握四个知识点：

1. **`PUT`**：通常表示用新数据替换原有资源。
2. **`PATCH`**：通常表示只修改指定字段，其余字段保持不变。
3. **`model_dump(exclude_unset=True)`**：找出客户端这次明确提交了哪些字段。
4. **`model_copy(update=...)`**：用这些字段生成更新后的模型对象。

我们从一个真实的 Agent 配置修改场景开始。

## 一、更新数据的基本场景

假设你已经创建了一个 Research Agent。

系统中保存着它的配置：

```json
{
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "max_steps": 5,
  "tools": ["search", "calculator"]
}
```

现在，用户打开设置页面，只想把：

```text
max_steps: 5 → 3
```

其他信息都不想改。

用户的真实意图是：

```text
原始 Agent 配置
        ↓
只修改 max_steps
        ↓
保存更新后的配置
```

  

      

更新前

        **Research Agent**
        
max_steps：5

tools：search、calculator

描述保持原样

    

      

更新后

        **Research Agent**
        
max_steps：3

tools：search、calculator

描述保持原样

    

  
仅 max_steps 发生变化；其他字段没有丢失。

假设前端只发送：

```json
{
  "max_steps": 3
}
```

后端必须正确理解：

> 用户没有提交 name、description、tools，并不意味着用户想把这些字段删除。

而本章最重要的问题就是：**怎样区分“客户端没有提交某个字段”和“客户端明确要求修改某个字段”。**

## 二、PUT：用新数据替换旧数据

首先复习 HTTP 请求方法。

| 方法 | 常见用途 |
|---|---|
| `GET` | 查询资源 |
| `POST` | 创建资源或提交任务 |
| `PUT` | 替换资源的当前表示 |
| `PATCH` | 部分修改现有资源 |
| `DELETE` | 删除资源 |

`PUT` 和 `PATCH` 都可以发送 JSON 请求体，也都能在 FastAPI 中使用 Pydantic 模型验证数据。

它们的典型区别是**更新语义**。

### 1. PUT 的替换式更新

假设数据库中原来保存：

```json
{
  "name": "Bar",
  "description": "The bartenders",
  "price": 62,
  "tax": 20.2,
  "tags": ["original"]
}
```

现在客户端执行：

```http
PUT /items/bar HTTP/1.1
Content-Type: application/json
```

Body：

```json
{
  "name": "Barz",
  "price": 3
}
```

客户端只发送了两个字段。

如果后端按照“替换整个对象”的方式处理，就不是只改变 name 和 price，而是使用新模型的完整数据替换旧对象。

对于官方教程所使用的带默认值模型，最后可能变成：

```json
{
  "name": "Barz",
  "description": null,
  "price": 3,
  "tax": 10.5,
  "tags": []
}
```

注意原来的：

```json
"tax": 20.2
```

变成了：

```json
"tax": 10.5
```

原来的：

```json
"tags": ["original"]
```

也变成了：

```json
"tags": []
```

因为这些字段没有在新请求中出现，Pydantic 使用了模型默认值，而服务器又把整个结果替换掉了。

这正是官方文档特别提醒的 **PUT 替换风险**。

### 2. 使用官方风格的 Item 模型

```python
from pydantic import BaseModel, Field


class Item(BaseModel):
    name: str | None = None
    description: str | None = None
    price: float | None = None
    tax: float = 10.5
    tags: list[str] = Field(default_factory=list)
```

这里你已经学过的默认值又派上用场了：

```python
tax: float = 10.5
```

表示如果请求中没有提供 tax，就使用 10.5。

```python
tags: list[str] = Field(default_factory=list)
```

表示如果请求中没有提供 tags，就生成一个空列表。

再看接口：

```python
from fastapi import FastAPI, HTTPException
from fastapi.encoders import jsonable_encoder

app = FastAPI()

items = {
    "bar": {
        "name": "Bar",
        "description": "The bartenders",
        "price": 62,
        "tax": 20.2,
        "tags": ["original"]
    }
}


@app.put("/items/{item_id}", response_model=Item)
def replace_item(item_id: str, item: Item):

    if item_id not in items:
        raise HTTPException(
            status_code=404,
            detail="Item not found"
        )

    # 转换为 JSON 兼容的 Python 数据
    encoded_item = jsonable_encoder(item)

    # 用新对象替换原来的对象
    items[item_id] = encoded_item

    return encoded_item
```

我们分析三行核心代码。

**第一行：**

```python
encoded_item = jsonable_encoder(item)
```

把 Pydantic 模型转换为 JSON 兼容的数据。

这里的结果是 Python 字典，不是 JSON 字符串。

**第二行：**

```python
items[item_id] = encoded_item
```

直接把原来的对象替换为新对象。

**第三行：**

```python
return encoded_item
```

把更新后的内容返回客户端。

因此，真正发生“替换”的不是 `@app.put()` 自动执行了某个魔法操作，而是这行代码：

```python
items[item_id] = encoded_item
```

**FastAPI 不会自动替你更新数据库。PUT 是 HTTP 方法，实际怎样修改数据由你的业务代码决定。**

## 三、PATCH：仅修改指定的字段

现在回到最初的 Agent 场景。

我们已经有：

```json
{
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "max_steps": 5,
  "tools": ["search", "calculator"]
}
```

用户发送：

```http
PATCH /agents/1 HTTP/1.1
Content-Type: application/json
```

Body：

```json
{
  "max_steps": 3
}
```

我们期待最终结果是：

```json
{
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "max_steps": 3,
  "tools": ["search", "calculator"]
}
```

也就是：

**只修改 max_steps，其他字段仍然使用原来的值。**

### 1. PUT 与 PATCH 对照

| 比较 | PUT | PATCH |
|---|---|---|
| 典型语义 | 替换现有资源 | 修改资源的部分字段 |
| 客户端常发送 | 一份完整的新资源表示 | 只需要修改的字段 |
| 没提交的字段 | 在替换实现中可能变为默认值或被删除 | 通常保持原值 |
| FastAPI 装饰器 | `@app.put(...)` | `@app.patch(...)` |
| 是否自动更新数据库 | 否 | 否 |

一个需要补充的细节：**PUT 和 PATCH 的具体更新行为最终仍取决于接口约定与服务器实现。** FastAPI 并不强制你必须如何解释它们。官方教程使用 PUT 展示替换、PATCH 展示部分更新，是为了说明两种常见设计。

## 四、部分更新的核心：exclude_unset=True

这是全章最需要真正理解的代码：

```python
item.model_dump(exclude_unset=True)
```

我们先不接数据库，也不写路由。

只看一个独立的 Python 例子。

```python
from pydantic import BaseModel


class AgentSettings(BaseModel):
    name: str = "Chat Agent"
    max_steps: int = 3
    debug: bool = False
```

现在用户只发送：

```json
{
  "max_steps": 5
}
```

FastAPI 构造的模型，相当于：

```python
settings = AgentSettings(max_steps=5)
```

注意：模型对象实际上仍然拥有三个字段。

```python
print(settings.name)
# Chat Agent

print(settings.max_steps)
# 5

print(settings.debug)
# False
```

因为没有提交的字段使用了默认值。

如果执行：

```python
print(settings.model_dump())
```

得到：

```python
{
    "name": "Chat Agent",
    "max_steps": 5,
    "debug": False
}
```

如果你拿这个完整字典去修改数据库，就有可能误把旧数据覆盖成这些默认值。

但是：

```python
print(
    settings.model_dump(exclude_unset=True)
)
```

得到：

```python
{
    "max_steps": 5
}
```

这就正确保留了客户端明确提交的字段。

### 1. exclude_unset 的含义

拆开英文：

- `exclude`：排除。
- `unset`：未显式设置。

所以：

```python
exclude_unset=True
```

表示：

> 生成字典时，排除实例创建时没有明确设置过的字段。

Pydantic 内部会记录哪些字段曾被显式提供；你还可以通过 `model_fields_set` 查看。

```python
print(settings.model_fields_set)
```

输出类似：

```python
{"max_steps"}
```

这就解释了为什么 `exclude_unset=True` 只留下 max_steps。

### 2. 三种容易混淆的情况

假设：

```python
class Settings(BaseModel):
    max_steps: int = 3
    description: str | None = None
```

| 客户端提交的 JSON | `model_dump(exclude_unset=True)` |
|---|---|
| `{}` | `{}` |
| `{"max_steps": 3}` | `{"max_steps": 3}` |
| `{"description": null}` | `{"description": None}` |

这三个结果非常重要。

**情况一：完全没有提交字段**

```json
{}
```

表示没有明确要求修改任何字段。

**情况二：明确提交了默认值**

```json
{
  "max_steps": 3
}
```

虽然 3 等于模型默认值，但用户确实发送了它，所以仍然保留。

**情况三：明确提交了 null**

```json
{
  "description": null
}
```

表示客户端明确设置了 description 为 `None`，所以也会保留。

因此：

**exclude_unset 排除的是“没有明确设置的字段”，而不是“值等于默认值的字段”，更不是“所有 None 字段”。**

## 五、错误的部分更新写法与正确写法

先看一段容易写错的代码：

```python
@app.patch("/items/{item_id}")
def update_item(item_id: str, item: Item):

    items[item_id] = item.model_dump()

    return items[item_id]
```

虽然用了：

```python
@app.patch(...)
```

但这里直接执行：

```python
item.model_dump()
```

会包含那些由模型自动填充的默认值。

假设客户端发送：

```json
{
  "price": 3
}
```

结果可能是：

```python
{
    "name": None,
    "description": None,
    "price": 3.0,
    "tax": 10.5,
    "tags": []
}
```

如果把这个结果直接存进原有数据，就又变成了替换。

因此，**仅仅把 `@app.put()` 改成 `@app.patch()`，并不能自动实现部分更新。**

### 正确流程

应该先获取已经保存的数据，再提取客户端明确提交的字段，最后合并。

```python
@app.patch("/items/{item_id}", response_model=Item)
def update_item(item_id: str, item: Item):

    # ① 读取旧数据
    stored_item_data = items[item_id]

    # ② 把旧数据转换为 Pydantic 模型
    stored_item_model = Item(**stored_item_data)

    # ③ 只提取用户明确提交的字段
    update_data = item.model_dump(
        exclude_unset=True
    )

    # ④ 将变更应用到旧模型的副本
    updated_item = stored_item_model.model_copy(
        update=update_data
    )

    # ⑤ 转换为 JSON 兼容数据并保存
    items[item_id] = jsonable_encoder(updated_item)

    # ⑥ 返回更新后的结果
    return updated_item
```

这是官方教程提供的核心思路。

接下来我们逐行理解其中尚未学过的部分。

## 六、model_copy(update=...)：把旧数据与新数据合并

你之前学习过：

```python
model_dump()
```

它用于把 Pydantic 模型转换成字典。

今天新增：

```python
model_copy()
```

它用于**复制一个 Pydantic 模型对象**。

例如：

```python
from pydantic import BaseModel


class AgentSettings(BaseModel):
    name: str
    max_steps: int
    debug: bool = False
```

原始对象：

```python
old_agent = AgentSettings(
    name="Research Agent",
    max_steps=5,
    debug=False
)
```

现在用户只想修改：

```python
update_data = {
    "max_steps": 3
}
```

执行：

```python
new_agent = old_agent.model_copy(
    update=update_data
)
```

得到：

```python
new_agent.model_dump()
```

结果：

```python
{
    "name": "Research Agent",
    "max_steps": 3,
    "debug": False
}
```

而且：

```python
old_agent.max_steps
# 5
```

仍然是 5。

为什么？

因为 `model_copy()` 创建了一个新对象，没有直接修改原来的模型对象。

### 它们的职责很清楚

```python
update_data = item.model_dump(
    exclude_unset=True
)
```

负责：

> 找出用户要求修改哪些字段。

```python
updated_item = stored_item_model.model_copy(
    update=update_data
)
```

负责：

> 复制旧模型，并用新的字段值覆盖相应属性。

所以可以把完整操作理解为：

  

    **旧数据**

    `{"name": "Research Agent", "max_steps": 5, "debug": false}`

  

    
用户提交 `{"max_steps": 3}`

  

    **提取明确提交的字段**

    `model_dump(exclude_unset=True)`

  

  

    **复制旧模型并更新指定字段**

    `old_agent.model_copy(update={"max_steps": 3})`

  

  

    **新数据**

    `{"name": "Research Agent", "max_steps": 3, "debug": false}`

### 重要补充：model_copy 不会自动重新验证数据

例如：

```python
old_agent.model_copy(
    update={"max_steps": "错误的值"}
)
```

`model_copy(update=...)` 本身不会重新运行 Pydantic 的字段验证。

这是 Pydantic 官方明确说明的行为。

为什么 FastAPI 官方示例仍然能使用？

因为进入函数之前，请求中的：

```python
item: Item
```

已经接受了 Pydantic 验证。

不过，真实项目如果还有复杂的跨字段规则、内部数据变更或嵌套对象，最好在合并后重新验证完整模型，避免保存无效数据。

本章提供的 Agent 实战代码就额外演示了这一步。

## 七、jsonable_encoder：转换成适合 JSON 存储的数据

你刚刚学习过：

```python
jsonable_encoder()
```

现在终于可以看到它在更新数据中的实际用途。

假设模型包含：

```python
from datetime import datetime
from pydantic import BaseModel


class AgentData(BaseModel):
    name: str
    updated_at: datetime
```

创建模型：

```python
agent = AgentData(
    name="Research Agent",
    updated_at=datetime(2026, 10, 29, 12, 30)
)
```

如果执行：

```python
agent.model_dump()
```

结果是包含 Python `datetime` 对象的字典：

```python
{
    "name": "Research Agent",
    "updated_at": datetime(2026, 10, 29, 12, 30)
}
```

但 JSON 并不直接支持 Python 的 datetime 对象。

执行：

```python
from fastapi.encoders import jsonable_encoder

encoded = jsonable_encoder(agent)
```

得到：

```python
{
    "name": "Research Agent",
    "updated_at": "2026-10-29T12:30:00"
}
```

现在它可以方便地用于 JSON 类型数据的存储或后续序列化。

### 在 PATCH 中的实际位置

```python
updated_item = stored_item_model.model_copy(
    update=update_data
)

items[item_id] = jsonable_encoder(updated_item)
```

第一部分：

```python
model_copy(update=...)
```

**创建更新后的模型。**

第二部分：

```python
jsonable_encoder(...)
```

**转换成 JSON 兼容的 Python 数据。**

第三部分：

```python
items[item_id] = ...
```

**把数据保存到本例使用的字典中。**

这三个动作完全不同。

特别注意：`jsonable_encoder()` 不会自动保存数据库，也不会执行字段合并。它只负责转换数据格式。

在 Pydantic v2 中，`model_dump(mode="json")` 也能对 Pydantic 模型进行类似的 JSON 兼容转换。

## 八、PATCH 中的 null、默认值与空列表

本节是非常值得练习的易错点。

假设当前 Agent 配置为：

```json
{
  "name": "Research Agent",
  "description": "负责搜索资料",
  "max_steps": 5,
  "tools": ["search", "calculator"]
}
```

下面四种请求代表四种不同的意图。

| PATCH 请求 JSON | 更新结果 |
|---|---|
| `{"max_steps": 3}` | 只把 max_steps 改成 3 |
| `{"description": null}` | 明确清空 description |
| `{"tools": []}` | 将工具列表替换成空列表 |
| `{}` | 没有提交任何变更字段 |

最重要的是：

```json
{}
```

和：

```json
{
  "description": null
}
```

**不是一回事。**

前者表示没有要求修改 description。

后者表示明确希望 description 变成 null。

因此，不能随意把：

```python
model_dump(exclude_unset=True)
```

换成：

```python
model_dump(exclude_none=True)
```

因为后者会丢弃值为 None 的字段。

如果用户本来就想清空 description，那么 `exclude_none=True` 可能导致这个修改被忽略。

还有一个细节：

```json
{
  "tools": []
}
```

通常表示把整个 tools 列表替换为空列表，**并不是对原列表执行“删除其中一个元素”**。

`model_copy(update=...)` 是浅层更新，不会自动对嵌套模型或列表进行递归合并。如果以后需要精准修改嵌套配置，应该另外设计更新规则。

## 九、结合《更多模型》设计真正的 Agent 更新接口

之前我们学习过：

```python
UserIn
UserOut
UserInDB
```

当时讲过：

> 输入模型、对外响应模型和内部模型不必完全一样。

更新数据时，同样应该这样设计。

假设我们的系统保存以下 Agent 数据：

```json
{
  "id": 1,
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "max_steps": 5,
  "tools": ["search", "calculator"],
  "owner_id": 42,
  "system_prompt": "内部系统提示词"
}
```

有两个字段不应该允许普通更新接口随意修改：

```text
owner_id
system_prompt
```

也不应该默认对外暴露它们。

因此可以分别定义：

| 模型 | 职责 |
|---|---|
| `AgentPut` | 完整替换可编辑的 Agent 配置 |
| `AgentPatch` | 只接收部分可编辑字段 |
| `AgentStored` | 内部存储数据，包含 owner_id、system_prompt |
| `AgentOut` | 对外公开的响应数据 |

### 1. 完整替换模型

```python
class AgentPut(BaseModel):
    name: str = Field(min_length=3)
    description: str | None = None
    max_steps: int = Field(default=3, ge=1, le=5)
    tools: list[str] = Field(default_factory=list)
```

其中 name 是必填的，而 max_steps、description、tools 都有默认值。

### 2. 部分更新模型

```python
class AgentPatch(BaseModel):

    model_config = {
        "extra": "forbid"
    }

    name: str | None = Field(
        default=None,
        min_length=3
    )

    description: str | None = None

    max_steps: int | None = Field(
        default=None,
        ge=1,
        le=5
    )

    tools: list[str] | None = None
```

这一段你要重点理解。

因为用户可能只发送：

```json
{
  "max_steps": 3
}
```

所以 PATCH 模型中的所有字段都应该允许省略。

这也正是 FastAPI 官方教程提出的建议：用于部分更新的输入模型，应允许不提交那些不需要修改的字段。

但是要区分：

```python
max_steps: int | None = None
```

中的两个作用：

- `= None`：允许省略。
- `int | None`：类型也允许显式传入 null。

我们的完整 Agent 模型不允许 max_steps 真正变成 None，因此示例业务代码还会明确拒绝这种修改。

**允许字段省略，不代表一定要允许字段最终变成 null。**

### 3. 更新接口的关键实现

```python
@app.patch(
    "/agents/{agent_id}",
    response_model=AgentOut
)
def patch_agent(
    agent_id: int,
    patch: AgentPatch
):

    # 查询已经保存的 Agent
    old_agent = get_stored_agent(agent_id)

    # 只获取明确提交的字段
    changes = patch.model_dump(
        exclude_unset=True
    )

    # 这里还需要检查不允许置为 null 的字段

    # 将修改应用到原有对象的副本
    candidate = old_agent.model_copy(
        update=changes
    )

    # 合并后重新验证完整对象
    updated = AgentStored.model_validate(
        candidate.model_dump()
    )

    # 保存 JSON 兼容形式
    AGENTS[agent_id] = jsonable_encoder(updated)

    return updated
```

这段是**核心流程示意**。随附的完整代码包含缺失 Agent 时的 404、禁止某些字段为 null、更新时间戳，以及对内部字段的保护。

### 4. Agent 身份和权限仍然需要验证

我们可以通过 PATCH 模型禁止客户端直接修改：

```text
owner_id
system_prompt
```

但这还不等于完成了授权。

真实系统仍要检查：

> 当前登录用户是否有权限修改这个 agent_id 对应的 Agent？

例如，不能仅凭用户知道：

```text
PATCH /agents/1
```

就允许他修改其他人的 Agent。

未来如果将 LangGraph 的模型、工具和系统提示词配置放入数据库，这一点尤其重要。

## 十二、本章易错点总结

| 常见混淆 | 正确理解 |
|---|---|
| 写了 `@app.patch()` 就会自动部分更新 | 不会，仍需自己实现字段合并 |
| `exclude_unset=True` 删除所有默认值 | 不对，明确提交的默认值仍保留 |
| `exclude_unset=True` 删除所有 None | 不对，显式提交的 null 仍保留 |
| `model_copy(update=...)` 会自动验证 | 不会自动重新验证 update 数据 |
| `model_copy()` 自动合并嵌套模型 | 普通用法是浅层更新，不自动递归合并 |
| `jsonable_encoder()` 会保存数据库 | 不会，它只转换数据格式 |
| PATCH 输入模型的所有字段都有默认值，就可以修改任何内部字段 | 不对，应该明确限定可编辑字段 |
| `response_model_exclude_unset=True` 与 `model_dump(exclude_unset=True)` 完全相同 | 底层筛选规则相近，但前者用于**控制响应输出**，后者在本章用于**提取更新字段** |

### 三道综合思考题

**思考题 1：预测更新结果**

旧 Agent 配置：

```json
{
  "name": "Research Agent",
  "max_steps": 5,
  "tools": ["search"]
}
```

客户端只发送：

```json
{
  "name": "New Agent"
}
```

假设模型默认 `max_steps=3`、`tools=[]`。

使用完整替换的 PUT 和使用 `exclude_unset=True` 的 PATCH，最终结果分别有什么不同？

**参考答案：**

PUT 可能使 max_steps 变成 3、tools 变成空列表。

PATCH 只修改 name，仍保留 max_steps=5 和 tools=["search"]。

**思考题 2：三个方法的职责**

解释下面三行：

```python
changes = patch.model_dump(exclude_unset=True)

updated = old.model_copy(update=changes)

stored_data = jsonable_encoder(updated)
```

**参考答案：**

第一行提取客户端明确提交的更新字段；第二行把这些更新应用于旧模型的副本；第三行转换成 JSON 兼容的 Python 数据。

注意：**第三行完成后，还没有自动保存到数据库。**

**思考题 3：Agent 配置安全**

Agent 的内部数据包含：

```python
name
max_steps
owner_id
system_prompt
```

但普通用户只允许修改 name 和 max_steps。

请设计一个 `AgentPatch` 模型，并说明为什么还需要权限验证。

**参考答案：**

```python
class AgentPatch(BaseModel):

    model_config = {
        "extra": "forbid"
    }

    name: str | None = None
    max_steps: int | None = None
```

它可以限制允许出现的更新字段，但还需要额外检查当前用户是否有权修改这个 Agent，不能只依赖模型校验。

## 十五、本章最终总结

真正需要记住的就是下面四行：

```python
old = Item(**stored_data)

changes = incoming.model_dump(exclude_unset=True)

updated = old.model_copy(update=changes)

items[item_id] = jsonable_encoder(updated)
```

它们依次完成：

**读取旧数据 → 提取明确的修改 → 合并修改 → 转换并保存。**
