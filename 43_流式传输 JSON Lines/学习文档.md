# 02｜流式传输 JSON Lines

**FastAPI 用户指南 · 逐章学习笔记｜概念优先、官方示例、Agent 应用、复习题**


官方文档：https://fastapi.tiangolo.com/zh/tutorial/stream-json-lines/

版本提示：官方说明内置的这组 JSON Lines 教程功能从 FastAPI 0.134.0 起提供。如果你用旧环境，示例可能不可直接照抄。

## 1. 什么叫 Streaming？

普通 JSON 返回通常是“工作全部完成 → 一次返回所有数据”。流式传输可以是“产生第 1 项 → 先发送第 1 项；产生第 2 项 → 发送第 2 项”。用户或另一个程序可以提前处理已到达的数据，但这并不保证总计算时间一定变短。

## 2. JSON Lines 的格式

普通 JSON 数组：

```json
[{"name":"Agent A"},{"name":"Agent B"}]
```

JSON Lines（JSONL）：

```jsonl
{"name":"Agent A"}
{"name":"Agent B"}
```

每行是一个**独立、合法的 JSON 值**，用换行符分隔；无需把整个序列封装成一个数组。官方使用的 Content-Type 是 `application/jsonl`，而非 `application/json`。

## 3. 官方写法：yield 连续产生数据项

下面保持官方结构，但用两个对象缩短示例：

```python
from collections.abc import AsyncIterable
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()
class Item(BaseModel):
    name: str

items = [Item(name='Agent A'), Item(name='Agent B')]

@app.get('/items/stream')
async def stream_items() -> AsyncIterable[Item]:
    for item in items:
        yield item
```

**逐句理解：** `AsyncIterable[Item]` 表示会产生一串 Item；`yield item` 每次提供一项，而不是 `return items` 一次性返回整组列表。FastAPI 可以逐项序列化并返回 JSON Lines。

官方还提供普通 `def` 配合 `Iterable[Item]`，或省略返回类型注解的版本。声明明确的输出类型有助于 FastAPI 使用 Pydantic 做验证、序列化与文档描述。

## 4. 为什么和上一章“依赖项”的 yield 不一样？

| 场景 | yield 交出去的是什么？ | 主要目的 |
| --- | --- | --- |
| Depends 中的 yield | 数据库会话等资源 | 使用结束后清理 |
| 流式路由函数中的 yield | 一个个结果项 | 边产生边发送 |

Python 的语法相同，使用场景与 FastAPI 对它的处理不同。

## 5. Agent 中可以做什么？

例如研究型 Agent 搜索、分析、生成报告三个阶段可逐步输出结构化记录：

```jsonl
{"step":"search","status":"completed"}
{"step":"analysis","status":"completed"}
{"step":"report","status":"completed"}
```

这只是 Agent 应用方案示意，不是官方原始样例。它更适合传给其他后端程序、数据消费端或需要逐行处理数据的客户端。

**边界：** JSON Lines 不是“自动开启 LLM 流式生成”的按钮。Agent 或模型本身也必须逐步产生结果。实际网络分包和代理缓冲可能影响客户端观察到的显示时机。

---

## 6. 为什么已经 yield 了，前端却没有逐步显示？

这一点对以后做 Agent 特别重要。**服务端能够分段产生数据，不等于浏览器必然逐段更新界面。** 如果客户端仍然调用一次 `response.json()` 等待整个响应结束，那么即使服务端用的是流式机制，用户仍可能只在最后看到全部结果。

真实流式体验一般需要三处配合：

- **生成端**：LLM / Agent 本身实际逐步产出文本或状态，而不是先把所有内容计算完。
- **传输端**：FastAPI 能够将每个数据项逐步发送；中间的代理与缓冲策略也会影响抵达时机。
- **接收端**：客户端按流读取、按换行拆分 JSON Lines，再根据每个 JSON 对象更新界面或任务记录。

尤其要注意：一次底层网络读取到的数据块（chunk）不一定刚好对应一条 JSON Lines 记录。一条记录可能被拆成多块，多条记录也可能合并在一块，因此接收端应按**换行符**提取完整 JSON 数据项，而不是假设“读到一次 chunk 就有一条完整 JSON”。

## 7. 再比较一下与 SSE 的使用场景

```text
后端 A → 研究任务进度数据 → 后端 B
    可以选择 JSON Lines，接收方按行解析结构化结果。

FastAPI → 前端聊天页面 → 进度、文字、完成事件
    可以选择 SSE，按照 event 类型更新不同界面区域。
```

两种方式都可能实现逐步展示，并不存在“JSON Lines 只能给后端、SSE 只能给浏览器”的硬性限制；选择取决于客户端对协议、事件结构和处理习惯的需要。

**应用提醒：**如果结果最终只是一个很短的 JSON 对象，强行采用流式传输并不会天然改善用户体验，还会增加客户端处理复杂度。

## 本章回顾与自测（附解析）

**题 1：JSON Lines 为什么适合持续发送多项结果？**
答案：每行是完整、独立的 JSON 值，客户端可以边收边解析，不必等数组完整。

**题 2：JSON Lines 响应是一个普通 JSON 数组吗？**
答案：不是。它不要求外层 `[]`，各行用换行符分开，Content-Type 为 `application/jsonl`。

**题 3：`yield` 在此章和 Depends 中作用一样吗？**
答案：语法相同但用途不同：流式路由逐条产生数据；带 yield 的依赖负责资源生命周期管理。

**题 4：把返回类型改为 `AsyncIterable[Item]` 就能让 LLM 立刻增量输出吗？**
答案：不能。内部模型或 Agent 本身必须逐步产出数据，客户端也要按流读取。

## 章节思考题（附参考方向）

**思考：如何向另一个后端服务逐条传递研究 Agent 的 search / analysis / report 状态？**
参考：每个步骤完成时产生结构化 JSON，并通过 JSON Lines 逐行发送；接收方按行解析更新任务记录。

**本章一句话总结：**JSON Lines 把连续的结构化结果一行一行发送；真正的流式体验还要求生产端逐步产出、客户端逐步处理。
