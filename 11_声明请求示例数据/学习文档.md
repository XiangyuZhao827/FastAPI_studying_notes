# 📘 FastAPI 新章节：声明请求示例数据（Declare Request Example Data）

FastAPI 零基础 → AI Agent 后端开发系列

官方教程：[FastAPI 中文官方文档：声明请求示例数据](https://fastapi.tiangolo.com/zh/tutorial/schema-extra-example/)

这一章和你刚学过的 **`Field()`、`BaseModel`、`Body()`** 联系非常紧密，而且实际开发 Agent API 时很有用。

先用一句话概括：

**这一章主要教你：如何为 API 的请求数据提供示例，让其他开发者在 `/docs` 中直接看到正确的 JSON 应该怎么写。**

它并不是教你如何让 Agent 生成示例回答，而是教你如何把**请求格式的使用说明**添加到 API 文档中。

## 一、为什么需要声明请求示例数据？

假设你已经定义了一个 Agent 对话接口：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class ChatRequest(BaseModel):
    message: str
    max_steps: int = 3
    session_id: str | None = None


@app.post("/chat")
def chat(request: ChatRequest):
    return {
        "answer": f"Agent 收到了：{request.message}"
    }
```

我们知道，这个接口应该使用 POST，并发送 JSON 请求体。

但假设你的前端开发同事第一次使用这个接口，他可能需要弄清楚：

- `message` 应该填写什么内容？
- `max_steps` 代表什么？
- `session_id` 应该是什么格式？
- 怎样填写一个完整、正确的 JSON？

即使 Swagger UI 已经显示字段类型，有一个真实的请求示例，仍然会让接口更容易理解。

例如：

```json
{
  "message": "请帮我解释 FastAPI",
  "max_steps": 3,
  "session_id": "session001"
}
```

这就是我们希望在 `/docs` 中展示的**请求示例数据**。

### 1. 最重要的区别：示例不等于默认值

请特别注意下面的对比。

```python
max_steps: int = Field(default=3)
```

表示：

> 如果客户端不提供 max_steps，Pydantic 使用默认值 3。

但：

```python
max_steps: int = Field(examples=[3])
```

表示：

> 在 API 文档里，展示一个 max_steps 可能填写的值：3。

这两个功能完全不同。

| 功能 | 写法 | 影响实际请求处理吗？ |
|---|---|---|
| 设置默认值 | `Field(default=3)` | 是，缺省时使用 3 |
| 限制合法范围 | `Field(ge=1, le=5)` | 是，非法数据无法通过验证 |
| 展示示例 | `Field(examples=[3])` | 否，只提供文档示例 |
| 说明字段含义 | `Field(description="最大步骤数")` | 否，主要用于文档 |

举个例子：

```python
max_steps: int = Field(
    default=3,
    ge=1,
    le=5,
    examples=[4]
)
```

此时：

- 不传 `max_steps` → 实际值是 **3**。
- 传 `max_steps=4` → 合法。
- 传 `max_steps=6` → 422。
- 文档中的示例值 → **4**。

**示例值不会替代默认值，也不会自动改变校验规则。**

## 二、官网第一种方法：给整个 Pydantic 模型添加示例

官方首先介绍 `model_config` 和 `json_schema_extra`。

### 1. 官方代码示例

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    description: str | None = None
    price: float
    tax: float | None = None

    model_config = {
        "json_schema_extra": {
            "examples": [
                {
                    "name": "Foo",
                    "description": "A very nice Item",
                    "price": 35.4,
                    "tax": 3.2
                }
            ]
        }
    }


@app.put("/items/{item_id}")
def update_item(item_id: int, item: Item):
    return {
        "item_id": item_id,
        "item": item
    }
```

这段代码与官网的 Pydantic v2 示例保持一致。

### 2. 我们来拆解最陌生的部分

```python
model_config = {
    "json_schema_extra": {
        "examples": [
            {
                "name": "Foo",
                "description": "A very nice Item",
                "price": 35.4,
                "tax": 3.2
            }
        ]
    }
}
```

不要被这段嵌套结构吓到。实际上，它只包含三个重要概念。

**第一层：`model_config`**

```python
model_config = {...}
```

它用于配置当前 Pydantic 模型的行为和元数据。

你在第 6 章已经见过：

```python
model_config = {"extra": "forbid"}
```

当时用于禁止额外字段。

现在它仍然是模型配置，只是使用了另一个配置选项。

**第二层：`json_schema_extra`**

```python
"json_schema_extra": {...}
```

表示：

> 为这个模型生成的 JSON Schema 添加额外信息。

JSON Schema 可以简单理解为**描述 JSON 数据结构的规则说明**。

FastAPI 会基于 Pydantic 模型生成 JSON Schema，并将它用于 OpenAPI 文档。

**第三层：`examples`**

```python
"examples": [
    {
        "name": "Foo",
        "price": 35.4
    }
]
```

这里是一个**列表**，列表中的每个元素是一个 JSON 对象形式的示例。

你之前学过 Python 的 `list` 和 `dict`：

```python
examples = [
    {"name": "Foo", "price": 35.4},
    {"name": "Bar", "price": 12.5}
]
```

这就是包含两个字典的 Python 列表。

因此：

```python
"examples": [...]
```

就是告诉文档系统：

> 这个模型可以参考这些示例来构造 JSON。

### 3. 最终客户端发送的 JSON 会变吗？

**不会。**

因为代码仍然是：

```python
def update_item(item_id: int, item: Item):
```

只有一个 Pydantic 请求体参数，并没有使用 `Body(embed=True)`。

所以正确的请求仍然是：

```text
PUT /items/123
```

Body：

```json
{
  "name": "Foo",
  "description": "A very nice Item",
  "price": 35.4,
  "tax": 3.2
}
```

而不需要额外包裹：

```json
{
  "item": {
    "name": "Foo",
    "price": 35.4
  }
}
```

**`json_schema_extra` 只增加文档信息，不改变 HTTP 请求体的结构。**

### 🤖 与 Agent 开发的联系

你可以给 `ChatRequest` 添加一个完整示例：

```python
class ChatRequest(BaseModel):
    message: str
    max_steps: int = 3
    session_id: str | None = None

    model_config = {
        "json_schema_extra": {
            "examples": [
                {
                    "message": "请帮我解释 Python",
                    "max_steps": 3,
                    "session_id": "session001"
                }
            ]
        }
    }
```

以后前端开发者打开 `/docs`，就能参考这个示例构造请求。

普通 Agent 用户依然只需要在聊天框中输入问题，前端负责把它自动组织成后端需要的 JSON。

## 三、官网第二种方法：使用 `Field(examples=[...])` 给单个字段添加示例

刚才是给整个模型提供一份完整的 JSON 示例。

但有时，我们只希望告诉前端开发者：

- name 可以填写 `"Foo"`。
- description 可以填写 `"A very nice Item"`。
- price 可以填写 `35.4`。

这时候就可以使用你上一章刚学过的 `Field()`。

### 1. 官网代码

```python
from pydantic import BaseModel, Field


class Item(BaseModel):
    name: str = Field(examples=["Foo"])

    description: str | None = Field(
        default=None,
        examples=["A very nice Item"]
    )

    price: float = Field(examples=[35.4])

    tax: float | None = Field(
        default=None,
        examples=[3.2]
    )
```

这是官方教程介绍的字段级示例写法。

### 2. 逐行理解

先看：

```python
name: str = Field(examples=["Foo"])
```

- `name`：字段名。
- `str`：字段类型是字符串。
- `Field(...)`：设置字段规则和元数据。
- `examples=["Foo"]`：文档中可以展示的字符串示例。

注意：

```python
["Foo"]
```

是 Python 列表。

即使我们只想展示一个示例，也使用列表形式。

再看：

```python
price: float = Field(examples=[35.4])
```

这里并没有设置默认值。

所以 `price` 仍然是必填字段。

**你不能把 `examples=[35.4]` 理解成 `default=35.4`。**

### 3. 与上一章 Field 的联系

例如：

```python
class ChatRequest(BaseModel):
    message: str = Field(
        min_length=1,
        max_length=2000,
        description="用户输入的问题",
        examples=["请帮我介绍 LangGraph"]
    )
```

这里包含两种不同的配置：

**校验规则：**

```python
min_length=1
max_length=2000
```

**文档信息：**

```python
description="用户输入的问题"
examples=["请帮我介绍 LangGraph"]
```

请求体校验由 Pydantic 负责；示例则帮助调用方理解字段应该填写什么。

## 四、官网第三种方法：使用 `Body(examples=[...])` 声明请求体示例

现在我们更进一步。

之前两种方式都是直接在 Pydantic 模型内部定义示例。

但 FastAPI 还允许你**直接在接口的 Body 参数上声明示例**。

### 1. 官方代码结构

```python
from typing import Annotated

from fastapi import Body, FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    price: float


@app.put("/items/{item_id}")
def update_item(
    item_id: int,
    item: Annotated[
        Item,
        Body(
            examples=[
                {
                    "name": "Foo",
                    "price": 35.4
                }
            ]
        )
    ]
):
    return {
        "item_id": item_id,
        "item": item
    }
```

重点是：

```python
item: Annotated[
    Item,
    Body(examples=[...])
]
```

你之前在第 7 章学过：

```python
Body()
```

它用于显式声明请求体参数。

现在我们给它添加了：

```python
examples=[...]
```

这样就能为当前接口的请求体提供示例。

### 2. 它与 model_config 有什么区别？

最容易理解的方式，是看它们分别写在哪里。

**方式 A：模型级示例**

```python
class Item(BaseModel):
    name: str
    price: float

    model_config = {
        "json_schema_extra": {
            "examples": [
                {"name": "Foo", "price": 35.4}
            ]
        }
    }
```

示例跟着 `Item` 模型。

**方式 B：接口请求体示例**

```python
@app.post("/items")
def create_item(
    item: Annotated[
        Item,
        Body(
            examples=[
                {"name": "Foo", "price": 35.4}
            ]
        )
    ]
):
    return item
```

示例写在具体接口的 Body 声明里。

两种方法都可以为 API 文档提供额外信息。

### 3. 可以添加多个 examples 吗？

当然可以。

```python
Body(
    examples=[
        {
            "name": "Foo",
            "price": 35.4
        },
        {
            "name": "Bar",
            "price": 28.5
        }
    ]
)
```

这里的 `examples` 是一个列表，包含两个字典。

但有个需要特别注意的地方：

**将多个示例加入 JSON Schema，不意味着 Swagger UI 一定会提供一个可以逐个切换这些示例的下拉菜单。**

FastAPI 官方因此还介绍了下一种方式：`openapi_examples`。

## 五、官网第四种方法：`Body(openapi_examples=...)` ⭐

这一部分是本章最值得掌握的知识点。

想象一下：

你正在开发 Agent API，希望前端同事打开 `/docs` 时，可以选择不同的请求示例：

- 普通对话。
- 简短执行。
- 故意错误的输入。

每个示例都应该有自己的名称和说明。

这时可以使用：

```python
Body(openapi_examples={...})
```

### 1. 官方示例的核心结构

```python
@app.put("/items/{item_id}")
def update_item(
    item_id: int,
    item: Annotated[
        Item,
        Body(
            openapi_examples={
                "normal": {
                    "summary": "A normal example",
                    "description": "A normal item works correctly.",
                    "value": {
                        "name": "Foo",
                        "price": 35.4
                    }
                },
                "converted": {
                    "summary": "An example with converted data",
                    "value": {
                        "name": "Bar",
                        "price": "35.4"
                    }
                },
                "invalid": {
                    "summary": "Invalid data",
                    "value": {
                        "name": "Baz",
                        "price": "not a number"
                    }
                }
            }
        )
    ]
):
    return {"item_id": item_id, "item": item}
```

其中的三个示例分别展示：

| 示例名称 | price | 实际发送后的结果 |
|---|---|---|
| normal | `35.4` | 合法浮点数 |
| converted | `"35.4"` | 默认非严格校验下一般可转换为浮点数 |
| invalid | `"not a number"` | 无法转换，返回 422 |

这正是官方示例想表达的重点：**API 文档可以同时展示正确输入、可转换输入和错误输入。** 

### 2. 逐层解释 openapi_examples

先看最外层：

```python
openapi_examples={
    "normal": {...},
    "converted": {...},
    "invalid": {...}
}
```

它是一个 Python 字典。

三个键：

```python
"normal"
"converted"
"invalid"
```

用于识别三个不同的示例。

再看每个示例内部：

```python
"normal": {
    "summary": "普通请求",
    "description": "一个可以成功执行的请求",
    "value": {
        "name": "Foo",
        "price": 35.4
    }
}
```

| 字段 | 意义 |
|---|---|
| `normal` | 示例标识 |
| `summary` | 简短标题 |
| `description` | 详细说明 |
| `value` | 真正展示的示例请求数据 |

`description` 还可以包含 Markdown 文本。

例如：

```python
"description": "这是一个 **普通** 请求。"
```

其中 `**普通**` 是 Markdown 的加粗语法。

### 3. 为什么错误示例也可以放在文档里？

这是一个特别容易误解的地方。

假设你声明：

```python
price: float
```

然后添加示例：

```python
"invalid": {
    "value": {
        "name": "Baz",
        "price": "hello"
    }
}
```

FastAPI 不会因为这个示例写在 `openapi_examples` 里，就认定它合法。

示例只是文档信息。

如果前端开发者在 `/docs` 中选择这个错误示例，并点击 **Execute**，请求仍然会经过真实的 Pydantic 校验。

于是：

```text
price = "hello"
        ↓
尝试解析为 float
        ↓
解析失败
        ↓
HTTP 422
```

这其实很有帮助。

因为开发者不仅能看到正确的请求写法，还能观察**不正确的请求会触发什么错误**。

### 4. 四种 examples 写法的最终对照

| 写法 | 示例针对的对象 | 数据结构 |
|---|---|---|
| `Field(examples=[...])` | 模型中的单个字段 | 列表 |
| `model_config = {"json_schema_extra": {"examples": [...]}}` | 整个 Pydantic 模型 | 列表 |
| `Body(examples=[...])` | 当前请求体的 JSON Schema | 列表 |
| `Body(openapi_examples={...})` | 当前接口的具名 OpenAPI 请求示例 | 字典 |

**我的建议：**现在先重点掌握 `Field(examples=...)` 和 `Body(openapi_examples=...)`，再理解 `model_config` 和普通 `Body(examples=...)` 的用途。

## 六、这些示例到底在哪里显示？

还记得 FastAPI 的三个重要地址吗？

```text
http://127.0.0.1:8000/docs
http://127.0.0.1:8000/redoc
http://127.0.0.1:8000/openapi.json
```

它们的作用不同。

| 地址 | 用途 |
|---|---|
| `/docs` | Swagger UI，可以查看示例并发送测试请求 |
| `/redoc` | 阅读 API 文档 |
| `/openapi.json` | 查看实际生成的 OpenAPI 规范 |

当你使用：

```python
Body(openapi_examples={...})
```

Swagger UI 通常会让你选择不同的具名请求示例。

而模型上的：

```python
model_config = {
    "json_schema_extra": {
        "examples": [...]
    }
}
```

则主要体现在生成的 JSON Schema 中。

如果你发现多个 `Body(examples=[...])` 并没有全部变成 Swagger UI 的可选择项目，这不代表没有添加成功。它们可以存在于 OpenAPI 的 JSON Schema 中，但展示方式取决于文档 UI 对这类示例的支持。

**不要把 Swagger UI 的展示功能和 FastAPI 的输入校验功能混为一谈。**

# 七、综合实战：为 Agent API 添加三种请求示例 🤖

现在把前面几章的知识组合起来。

我们要创建一个 Agent 对话接口：

```text
POST /agents/2/chat
```

用户的前端客户端会自动发送 JSON，而其他开发者可以在 `/docs` 中看到三种示例：

1. 普通对话。
2. 简短执行。
3. 故意错误的请求。

## 1. 完整可运行代码

新建文件：

`agent_request_examples.py`

```python
from typing import Annotated

from fastapi import (
    Body,
    FastAPI,
    HTTPException,
    Path,
    Query,
)
from pydantic import BaseModel, Field


app = FastAPI(
    title="Agent API - Request Examples"
)


# ===== 一、模拟 Agent 数据库 =====

AGENTS = {
    1: "Chat Agent",
    2: "Code Agent",
    3: "Research Agent",
}


# ===== 二、请求体模型 =====

class AgentRequest(BaseModel):

    message: str = Field(
        min_length=1,
        max_length=1000,
        description="用户发送给 Agent 的问题",
        examples=["请帮我解释 FastAPI"],
    )

    session_id: str | None = Field(
        default=None,
        description="会话标识",
        examples=["session001"],
    )

    max_steps: int = Field(
        default=3,
        ge=1,
        le=5,
        description="模拟 Agent 执行步骤数",
        examples=[3],
    )

    tags: list[str] = Field(
        default_factory=list,
        description="任务标签",
        examples=[["python", "fastapi"]],
    )

    # 整个请求模型的示例
    model_config = {
        "json_schema_extra": {
            "examples": [
                {
                    "message": "请帮我解释 Python",
                    "session_id": "session001",
                    "max_steps": 3,
                    "tags": ["python"],
                }
            ]
        }
    }


# ===== 三、响应模型 =====

class AgentResponse(BaseModel):
    agent_id: int
    agent_name: str
    answer: str
    steps: list[str]
    session_id: str | None = None


# ===== 四、Agent 接口 =====

@app.post(
    "/agents/{agent_id}/chat",
    response_model=AgentResponse,
)
def chat(

    agent_id: Annotated[
        int,
        Path(ge=1, examples=[2])
    ],

    request: Annotated[
        AgentRequest,
        Body(
            openapi_examples={

                "normal": {
                    "summary": "普通对话",
                    "description": "一个可以成功执行的请求。",
                    "value": {
                        "message": "请帮我解释 FastAPI",
                        "session_id": "session001",
                        "max_steps": 3,
                        "tags": ["python"],
                    },
                },

                "short": {
                    "summary": "简短执行",
                    "description": "只模拟一步。",
                    "value": {
                        "message": "你好，Agent",
                        "max_steps": 1,
                    },
                },

                "invalid": {
                    "summary": "错误输入（演示 422）",
                    "description": "消息为空，步骤数超限。",
                    "value": {
                        "message": "",
                        "max_steps": 99,
                    },
                },
            }
        ),
    ],

    debug: Annotated[
        bool,
        Query(examples=[False])
    ] = False,

):

    # 检查 Agent 是否存在
    if agent_id not in AGENTS:
        raise HTTPException(
            status_code=404,
            detail="Agent not found",
        )

    # 模拟 Agent 工作流
    planned_steps = [
        "理解问题",
        "制定计划",
        "调用模拟工具",
        "整理信息",
        "输出回答",
    ]

    steps = planned_steps[:request.max_steps]

    answer = (
        f"{AGENTS[agent_id]} 收到了：{request.message}"
    )

    if debug:
        answer += "（调试模式）"

    return AgentResponse(
        agent_id=agent_id,
        agent_name=AGENTS[agent_id],
        answer=answer,
        steps=steps,
        session_id=request.session_id,
    )
```

### 2. 新增了哪些知识？

实际上，本例把四种示例声明方式结合在一起。

| 位置 | 使用的功能 |
|---|---|
| `message` 字段 | `Field(examples=[...])` |
| `AgentRequest` 模型 | `model_config` + `json_schema_extra` |
| `agent_id` 路径参数 | `Path(examples=[2])` |
| `debug` 查询参数 | `Query(examples=[False])` |
| `request` 请求体 | `Body(openapi_examples={...})` |

这说明示例不仅适用于 JSON Body，也可以用于 Path 和 Query 等参数的 API 文档。

## 八、本章与此前知识以及真实 Agent 的联系

到现在，我们可以把之前学到的内容连接成这样：

```text
普通用户在网页聊天框输入问题
             ↓
前端按照 API 文档约定构造 JSON
             ↓
发送 POST /agents/2/chat
             ↓
FastAPI 根据 Path、Query、Body 提取数据
             ↓
Pydantic 根据 Field 校验字段
             ↓
业务层检查 Agent 是否存在
             ↓
Agent / LangGraph / LLM 真正执行
             ↓
response_model 规范输出
             ↓
前端展示回答
```

那么，本章新增的 `examples` 在哪里发挥作用？

**它主要作用于“前端按照 API 文档约定构造 JSON”这一环节。**

让其他开发者更容易知道：

- 请求 URL 怎么写。
- JSON 应该包含什么字段。
- 字段应该填什么样的数据。
- 正常示例是什么。
- 错误输入可能是什么样子。

但下面这些事情并不会因为添加示例而自动发生：

- Agent 不会自动获得训练数据。
- LLM 不会自动生成更好的答案。
- LangGraph 不会自动限制执行步骤。
- 数据库不会自动创建测试数据。
- API 不会自动完成身份认证。

**示例是帮助使用和理解 API 的文档，不是执行 Agent 的业务逻辑。**

## 九、常见错误总结

| 容易混淆的概念 | 正确理解 |
|---|---|
| `examples` 和 `default` | 前者是展示示例，后者是真实默认值 |
| `examples` 和 `Field(ge=1)` | 前者不校验，后者会校验 |
| `Field(examples=...)` | 给单个模型字段添加示例 |
| `json_schema_extra` | 给整个模型的 JSON Schema 添加信息 |
| `Body(examples=...)` | 请求体的 JSON Schema 示例 |
| `Body(openapi_examples=...)` | OpenAPI 中可具名的多个请求示例 |
| `examples` 与 `embed=True` | 前者只提供示例，后者改变请求体嵌套结构 |
| 文档中的错误示例 | 真正提交后仍可能返回 422 |

# 一、思考题 2：给 ChatRequest 添加字段示例和完整模型示例

**题目：**

设计一个 `ChatRequest`，包含 `message`、`max_steps`、`session_id` 三个字段。给每个字段添加 `Field(examples=...)`，再给整个模型添加一份完整的 JSON 示例。

## 1. 完整参考代码

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


class ChatRequest(BaseModel):

    # 用户输入的问题
    message: str = Field(
        min_length=1,
        max_length=2000,
        description="用户发送给 Agent 的问题",
        examples=["请帮我解释 FastAPI"]
    )

    # Agent 执行配置
    max_steps: int = Field(
        default=3,
        ge=1,
        le=5,
        description="Agent 最大执行步骤数",
        examples=[3]
    )

    # 会话标识
    session_id: str | None = Field(
        default=None,
        description="当前对话的会话 ID",
        examples=["session001"]
    )

    # 整个请求体的完整示例
    model_config = {
        "json_schema_extra": {
            "examples": [
                {
                    "message": "请帮我解释 FastAPI",
                    "max_steps": 3,
                    "session_id": "session001"
                }
            ]
        }
    }


@app.post("/chat")
def chat(request: ChatRequest):
    return {
        "answer": f"Agent 收到了：{request.message}",
        "max_steps": request.max_steps,
        "session_id": request.session_id
    }
```

这段代码可以直接保存为 `main.py`，然后使用：

```bash
fastapi dev main.py
```

运行后打开：

```text
http://127.0.0.1:8000/docs
```

就可以查看请求模型及其示例。

## 2. 字段级 examples 和模型级 examples 的区别

这是本题最重要的考点。

### 第一种：字段级示例

```python
message: str = Field(
    examples=["请帮我解释 FastAPI"]
)
```

这里的：

```python
examples=["请帮我解释 FastAPI"]
```

仅仅为 `message` 这一个字段添加示例。

类似地：

```python
max_steps: int = Field(
    default=3,
    examples=[3]
)
```

仅为 `max_steps` 添加示例。

也就是说，**字段级示例是分别说明每个字段可以填写什么**。

### 第二种：模型级示例

```python
model_config = {
    "json_schema_extra": {
        "examples": [
            {
                "message": "请帮我解释 FastAPI",
                "max_steps": 3,
                "session_id": "session001"
            }
        ]
    }
}
```

这一段提供的是一份**完整的 JSON 请求体示例**。

它告诉调用方，三个字段组合起来应该是什么结构：

```json
{
  "message": "请帮我解释 FastAPI",
  "max_steps": 3,
  "session_id": "session001"
}
```

可以这样比较：

| 对比 | `Field(examples=...)` | `json_schema_extra` |
|---|---|---|
| 作用范围 | 单个字段 | 整个模型 |
| 示例内容 | 单个字段的值 | 完整 JSON 对象 |
| 写在哪里 | Field 内部 | BaseModel 的 model_config |
| 是否影响校验 | 否 | 否 |
| 主要用途 | 解释字段如何填写 | 展示完整请求格式 |

### 3. 有一个容易弄错的细节

看下面这行：

```python
max_steps: int = Field(
    default=3,
    examples=[5]
)
```

这里的：

- `default=3`：真实默认值。
- `examples=[5]`：文档中的示例值。

用户如果没有提交 `max_steps`，**实际使用的是 3，而不是 5**。

而且无论示例填写什么，都不影响 `ge`、`le` 等验证规则。

## 4. 请求示例与响应示例

当用户调用：

```text
POST /chat
```

请求体：

```json
{
  "message": "请帮我解释 FastAPI",
  "max_steps": 3,
  "session_id": "session001"
}
```

在当前程序中，会返回：

```json

  "answer": "Agent 收到了：请帮我解释 FastAPI",

}
```

**思考题 2 总结：**

`Field(examples=...)` 用来解释模型中的单个字段，`model_config["json_schema_extra"]["examples"]` 用来展示整个请求体应该如何组合。这两者都是文档信息，不会改变实际的默认值和验证规则。

# 二、思考题 3：为什么前端开发者需要 Swagger 示例，而普通用户不需要？

**题目：**

在真实 Agent 项目中，为什么前端开发者需要了解 Swagger 示例，而普通用户通常只需要在聊天框中输入问题？

请从前端、FastAPI、Pydantic、Agent 执行器四个层次解释。

## 1. 首先要理解：用户和开发者看到的是不同的东西

普通用户看到的聊天界面可能是：

  

    **AI Agent 聊天助手**

  

你好！请告诉我你想了解什么。

  

      
请帮我解释 FastAPI

    

  
示意界面：用户只负责输入问题。

用户根本不需要知道什么是：

```python
BaseModel
Field()
Body()
```

也不需要自己写：

```json
{
  "message": "请帮我解释 FastAPI",
  "max_steps": 3,
  "session_id": "session001"
}
```

因为**这些 JSON 数据通常由前端程序自动构造**。

## 2. 第一层：前端客户端

假设用户输入：

> 请帮我解释 FastAPI

前端程序读取用户输入，并根据后端规定的 API 格式构造 JSON。

例如：

```javascript
const userInput = "请帮我解释 FastAPI";

const requestBody = {
    message: userInput,
    max_steps: 3,
    session_id: "session001"
};

const response = await fetch(
    "/chat",
    {
        method: "POST",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify(requestBody)
    }
);

const result = await response.json();

console.log(result.answer);
```

这里最关键的是：

```javascript
body: JSON.stringify(requestBody)
```

它将前端构造的 JavaScript 对象转换成 JSON 格式并发送。

**那么前端开发者为什么需要 Swagger 示例？**

因为前端开发者必须知道后端要求的数据格式。

例如，后端要求：

```json
{
  "message": "你好"
}
```

前端却发送：

```json
{
  "question": "你好"
}
```

就可能由于缺少必填的 `message` 字段而得到 HTTP 422。

Swagger 示例可以帮助前端开发者了解请求应该如何构造，减少字段名和嵌套结构上的错误。

## 3. 第二层：FastAPI 后端

前端发送：

```text
POST /chat
```

Body：

```json
{
  "message": "请帮我解释 FastAPI",
  "max_steps": 3,
  "session_id": "session001"
}
```

FastAPI 接口定义：

```python
@app.post("/chat")
def chat(request: ChatRequest):
    ...
```

FastAPI 的工作是：

**接收 HTTP 请求，找到对应路由，并根据函数参数声明确定请求体应该解析成什么类型。**

由于 `ChatRequest` 是 Pydantic 模型，FastAPI 会将 JSON 数据交给 Pydantic 解析和验证。

## 4. 第三层：Pydantic 验证

假设模型为：

```python
class ChatRequest(BaseModel):
    message: str = Field(min_length=1)
    max_steps: int = Field(default=3, ge=1, le=5)
```

Pydantic 负责检查：

- message 是否提供。
- message 是否是合法字符串。
- message 是否满足最小长度。
- max_steps 是否是合法整数。
- max_steps 是否处于 1～5 的范围。

如果输入非法，就会阻止它正常进入业务函数，并由 FastAPI 返回 HTTP 422。

如果输入正确，则函数内部可以直接使用：

```python
request.message
request.max_steps
```

这里你应该已经能发现：

**FastAPI 和 Pydantic 并不负责理解用户的问题。它们只负责把收到的 HTTP 数据转换成符合规则的 Python 对象。**

## 5. 第四层：Agent 执行器

这是实际回答用户问题的地方。

例如未来你可能写：

```python
@app.post("/chat")
def chat(request: ChatRequest):

    answer = run_agent(
        message=request.message,
        max_steps=request.max_steps
    )

    return {"answer": answer}
```

其中：

```python
run_agent(...)
```

是假设你将来实现的 Agent 执行函数。

它内部可能使用：

- LLM 生成回答。
- LangGraph 管理工作流。
- Tools 搜索资料、调用工具。
- 数据库存储和读取会话状态。

注意，`max_steps` 只有被实际执行逻辑使用，才会限制 Agent 的运行过程；仅仅把它定义成一个 `Field()` 字段并不会自动控制 LangGraph。

## 6. 把完整流程串起来

  

    **普通用户**
    
输入：请帮我解释 FastAPI

  

  

    **前端客户端**
    
参考 API 契约自动封装 JSON，请求 POST /chat

  

  

    **FastAPI**
    
匹配路由、读取 HTTP 请求体、识别 ChatRequest

  

  

    **Pydantic**
    
使用 BaseModel 和 Field 进行输入验证

  

  

    **Agent / LangGraph / LLM**
    
执行任务、调用模型或工具，生成回答

  

  

    **前端展示回答**
    
用户看到 Agent 的结果

## 7. 思考题 3 的标准答题表达

如果你在考试或面试中遇到这道题，可以这样回答：

> 普通 Agent 用户只需要输入自然语言问题，因为前端客户端会自动将用户输入封装成符合后端 API 要求的 JSON 请求体。前端开发者需要参考 Swagger UI 中的请求示例，以了解接口的字段名称、数据类型和 JSON 结构，从而正确调用 FastAPI。
>
> FastAPI 负责接收请求并解析参数，Pydantic 负责根据 BaseModel 和 Field 对输入数据进行验证。通过验证后，业务逻辑将用户消息及运行配置交给 Agent 执行器，最终调用 LLM、工具或 LangGraph 工作流来完成任务。
>
> 因此，Swagger 请求示例主要服务于 API 开发与调试，而不是让普通用户手工填写 JSON。

## 三、你应该真正记住的区别

| 概念 | 解决的问题 |
|---|---|
| `Field(examples=...)` | 单个字段可以怎么填写？ |
| `json_schema_extra` | 一份完整 JSON 请求是什么样？ |
| Swagger UI `/docs` | 开发者怎样查看和测试 API？ |
| 前端客户端 | 怎样把用户输入自动封装为 JSON？ |
| FastAPI | 怎样接收并解析 HTTP 请求？ |
| Pydantic | 怎样验证输入是否合法？ |
| Agent 执行器 | 怎样真正执行用户任务并生成回答？ |

**最核心的结论是：示例数据帮助开发者正确调用 API，而不是替代用户输入，更不是 Agent 的执行逻辑。**

你把这个区别弄清楚后，之前学过的 `Path`、`Query`、`Body`、`BaseModel`、`Field` 和这一章的 `examples`，就都能放进一个完整的 Agent 系统中理解了。
