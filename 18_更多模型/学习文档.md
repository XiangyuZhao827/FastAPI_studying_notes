# 第二章：更多模型（Extra Models）

## 一、为什么同一个对象需要多个模型？

上一章我们学会了：

```python
@app.post("/chat", response_model=ChatResponse)
```

其中：

```python
ChatRequest
```

负责接收请求。

```python
ChatResponse
```

负责输出响应。

但假设我们现在开始开发一个真正的用户系统。

用户注册时需要提供：

```json
{
  "username": "tom",
  "email": "tom@example.com",
  "password": "my-password"
}
```

于是我们创建：

```python
class User(BaseModel):
    username: str
    email: str
    password: str
```

这个模型似乎同时能够用于：

- 注册用户。
- 保存用户信息。
- 返回用户信息。

可是问题来了：

**当别人查询用户资料时，你绝对不应该把用户密码也返回出去。**

此外，数据库也不应该直接保存原始明文密码。

因此，我们需要把一个“用户”在不同环节中的数据区分开。

  

    **UserIn — 用户输入模型**

    `username` · `email` · `password`

  

  

    **UserInDB — 内部存储模型**

    `username` · `email` · `hashed_password`

真正应用中需要使用专门的安全密码哈希算法

  

  

    **UserOut — 对外响应模型**

    `username` · `email`

这正是 FastAPI 官方《更多模型》章节的主要思想。

---

## 二、官方例子：三个用户模型

先看经过简化的代码：

```python
from pydantic import BaseModel


class UserIn(BaseModel):
    username: str
    password: str
    email: str
    full_name: str | None = None


class UserOut(BaseModel):
    username: str
    email: str
    full_name: str | None = None


class UserInDB(BaseModel):
    username: str
    email: str
    hashed_password: str
    full_name: str | None = None
```

官方例子使用 `EmailStr` 作为 email 类型。为了让你不用安装额外依赖就能复制运行，我先写成 `str`。

如果你想使用更完善的邮箱格式验证，可以安装：

```bash
pip install "pydantic[email]"
```

然后改为：

```python
from pydantic import EmailStr

email: EmailStr
```

### 1. UserIn：客户端输入模型

```python
class UserIn(BaseModel):
    username: str
    password: str
    email: str
    full_name: str | None = None
```

客户端注册时发送：

```json
{
  "username": "tom",
  "password": "example-password",
  "email": "tom@example.com"
}
```

这里客户端必须提供密码，因为注册流程需要验证并安全地处理它。

### 2. UserOut：对外响应模型

```python
class UserOut(BaseModel):
    username: str
    email: str
    full_name: str | None = None
```

这个模型没有：

```python
password
hashed_password
```

所以客户端收到的用户资料可以是：

```json
{
  "username": "tom",
  "email": "tom@example.com",
  "full_name": null
}
```

### 3. UserInDB：内部存储模型

```python
class UserInDB(BaseModel):
    username: str
    email: str
    hashed_password: str
    full_name: str | None = None
```

这个模型用来描述服务端内部的数据。

例如：

```python
UserInDB(
    username="tom",
    email="tom@example.com",
    hashed_password="some-secure-password-hash"
)
```

注意：

- `password`：用户提交的原始密码。
- `hashed_password`：使用安全密码哈希算法处理后的结果。

二者不能混为一谈。

官方教程里的 `fake_password_hasher()` 只是说明数据流程，不是一个真正安全的密码哈希函数，不能直接用于生产环境。

## 三、上一章和这一章是如何连接的？

看下面这个接口：

```python
@app.post("/users/", response_model=UserOut)
def create_user(user: UserIn):
    return {
        "username": user.username,
        "email": user.email,
        "full_name": user.full_name
    }
```

这里出现了两个模型。

**输入：**

```python
user: UserIn
```

表示注册数据需要符合 UserIn。

**输出：**

```python
response_model=UserOut
```

表示最终响应应该符合 UserOut。

你还可以在后端先构造 `UserInDB`，但不能因此把数据库内部数据原封不动暴露给客户端。

这就是“更多模型”的核心思想：

**同一个业务对象，可以根据用途定义不同的数据结构。**

## 四、官方重点：`model_dump()` 和 `**` 字典解包

这部分和你之前学过的 Python 基础知识直接相关。

官方教程介绍了：

```python
user_in.model_dump()
```

以及：

```python
UserInDB(**user_in.model_dump(), hashed_password=...)
```

我们先分别理解它们。

### 1. model_dump() 做什么？

假设：

```python
user_in = UserIn(
    username="tom",
    password="example-password",
    email="tom@example.com"
)
```

现在：

```python
user_dict = user_in.model_dump()
```

得到的是 Python 字典：

```python
{
    "username": "tom",
    "password": "example-password",
    "email": "tom@example.com",
    "full_name": None
}
```

重点：

**`model_dump()` 返回 Python `dict`，并不是直接生成 HTTP 响应，也不等同于返回 JSON 字符串。**

你还记得之前的区别吗？

```python
user_in.username
```

适用于模型对象。

```python
user_dict["username"]
```

适用于 Python 字典。

### 2. `**` 是什么意思？

假设我们有：

```python
data = {
    "username": "tom",
    "email": "tom@example.com"
}
```

下面两种写法效果相同：

```python
UserOut(
    username="tom",
    email="tom@example.com"
)
```

```python
UserOut(**data)
```

其中：

```python
**data
```

表示将字典的键值对展开成关键字参数。

可以理解成：

```python
username="tom",
email="tom@example.com"
```

这就是**字典解包**。

### 3. 如何从 UserIn 创建 UserInDB？

这里我给你一个比直接复制所有字段更清晰的教学写法：

```python
data = user_in.model_dump(
    exclude={"password"}
)
```

它会生成：

```python
{
    "username": "tom",
    "email": "tom@example.com",
    "full_name": None
}
```

注意，原始密码被排除在外。

假设我们已经通过安全密码哈希函数生成了：

```python
hashed_password = "some-secure-password-hash"
```

然后：

```python
user_in_db = UserInDB(
    **data,
    hashed_password=hashed_password
)
```

就相当于：

```python
user_in_db = UserInDB(
    username="tom",
    email="tom@example.com",
    full_name=None,
    hashed_password="some-secure-password-hash"
)
```

当然，这里的 `hashed_password` 是占位示例，真实应用必须用合适的密码哈希库生成，而不能人为编造哈希字符串。

### 4. 为什么官方代码看起来还传了 password？

官方示例使用：

```python
UserInDB(
    **user_in.model_dump(),
    hashed_password=hashed_password
)
```

这里的 `model_dump()` 会包含 `password`。

由于 Pydantic 模型默认通常忽略未声明的额外字段，而 `UserInDB` 没有定义 `password`，这个示例可以正常构建模型。

但如果未来修改了模型的额外字段处理配置，例如使用 `extra="forbid"`，这种做法就可能不再适用。

更重要的是，在真实密码处理流程中，我建议你**明确排除原始 password**，不要让不需要它的内部模型继续接触明文密码。

## 五、官方重点：使用模型继承减少重复 ⭐

你有没有注意到？

刚才的三个模型里面，以下字段都出现了：

```python
username: str
email: str
full_name: str | None = None
```

如果你以后把 username 的规则修改成：

```python
username: str = Field(min_length=3)
```

是不是要修改三个模型？

这样很容易漏掉。

所以官方教程提供了一种更好的设计：**继承**。

### 1. 什么是继承？

先定义一个基础模型：

```python
class UserBase(BaseModel):
    username: str
    email: str
    full_name: str | None = None
```

然后：

```python
class UserIn(UserBase):
    password: str
```

这里：

```python
UserIn(UserBase)
```

表示：

> UserIn 继承 UserBase 中已经定义的字段和验证规则。

因此 UserIn 实际拥有：

```python
username
email
full_name
password
```

而不需要把前面三个字段重新写一遍。

### 2. 三个模型都继承 UserBase

```python
from pydantic import BaseModel


class UserBase(BaseModel):
    username: str
    email: str
    full_name: str | None = None


class UserIn(UserBase):
    password: str


class UserOut(UserBase):
    pass


class UserInDB(UserBase):
    hashed_password: str
```

这段代码比前面清晰很多。

尤其注意：

```python
class UserOut(UserBase):
    pass
```

`pass` 在 Python 中表示：

> 这里不额外增加任何字段。

也就是说，UserOut 直接继承 UserBase 中的：

```python
username
email
full_name
```

没有新增 password。

### 3. 一张表看懂继承之后的字段

| 模型 | username | email | full_name | password | hashed_password |
|---|---|---|---|---|---|
| `UserBase` | ✓ | ✓ | ✓ | — | — |
| `UserIn` | ✓ | ✓ | ✓ | ✓ | — |
| `UserOut` | ✓ | ✓ | ✓ | — | — |
| `UserInDB` | ✓ | ✓ | ✓ | — | ✓ |

这里的设计原则是：

**公共字段写在父模型中，不同用途需要的额外字段写在子模型中。**

### 🤖 Agent 项目中怎样复用这种设计？

你完全可以按照相同思路组织 Agent 数据。

```python
class AgentBase(BaseModel):
    name: str
    description: str | None = None


class AgentCreate(AgentBase):
    system_prompt: str


class AgentOut(AgentBase):
    id: int


class AgentInDB(AgentBase):
    id: int
    system_prompt: str
    owner_id: int
```

这样：

- `AgentCreate`：创建 Agent 时的输入。
- `AgentOut`：对普通客户端展示的 Agent 信息。
- `AgentInDB`：内部使用的 Agent 数据，包含所有者标识及系统提示词等字段。

在这个设计中：

**客户端查询 Agent 信息时，不需要因为数据库里有 `system_prompt`，就把它也返回出去。**

当然，某些受授权的管理接口可以设计单独的管理响应模型，按权限返回更多字段。

## 六、使用 Union：当响应可能有不同的数据结构

假设你正在开发一个 Agent 系统。

有些请求，Agent 只需要返回文本：

```json
{
  "kind": "text",
  "answer": "你好"
}
```

另外一些请求，Agent 可能调用了工具，需要返回：

```json
{
  "kind": "tool",
  "answer": "计算完成",
  "tools_used": ["calculator"]
}
```

你发现了吗？

两种响应结构并不完全相同：

- 普通文本回答没有 `tools_used`。
- 工具回答多了一个 `tools_used` 列表。

这时候我们可以定义两个模型。

```python
from typing import Literal
from pydantic import BaseModel


class TextResult(BaseModel):
    kind: Literal["text"]
    answer: str


class ToolResult(BaseModel):
    kind: Literal["tool"]
    answer: str
    tools_used: list[str]
```

这里的：

```python
Literal["text"]
```

表示 kind 只能是 `"text"`。

而：

```python
Literal["tool"]
```

表示只能是 `"tool"`。

接下来：

```python
@app.get(
    "/results/{kind}",
    response_model=TextResult | ToolResult
)
def get_result(kind: str):

    if kind == "tool":
        return {
            "kind": "tool",
            "answer": "计算完成",
            "tools_used": ["calculator"]
        }

    return {
        "kind": "text",
        "answer": "你好"
    }
```

最关键的是：

```python
response_model=TextResult | ToolResult
```

它表示：

> 当前接口的响应可以符合 TextResult，也可以符合 ToolResult。

这相当于：

```python
from typing import Union

response_model=Union[TextResult, ToolResult]
```

现代 Python 和 FastAPI 可以使用前面的 `|` 形式。我已经用当前 FastAPI/Pydantic 环境实际验证了这种写法。

### 1. OpenAPI 中会出现什么？

FastAPI 会为这种联合响应生成相应的 Schema，常见的是：

```json
{
  "anyOf": [
    {"$ref": "#/components/schemas/TextResult"},
    {"$ref": "#/components/schemas/ToolResult"}
  ]
}
```

你暂时不用记住 `$ref` 的细节。

理解：

```text
anyOf
```

表示响应可以符合多个候选 Schema 之一。

官方教程也是使用“汽车模型或飞机模型”来说明这种情况。

### 2. 一个值得注意的细节

如果多个模型的字段非常相似，Pydantic 有时需要根据模型规则判断如何选择联合类型中的分支。

因此，对于 Agent API，我建议像上面一样使用：

```python
kind: Literal["text"]
```

和：

```python
kind: Literal["tool"]
```

用一个明确的字段帮助区分响应类型。

这比依赖某个字段是否恰巧存在，更容易让前端理解。

## 七、返回模型列表：`response_model=list[Model]`

你在之前的学习中已经接触过：

```python
list[str]
```

以及：

```python
list[Message]
```

现在我们将它用于**响应**。

假设一个 Agent 管理接口需要返回多个 Agent：

```python
class AgentOut(BaseModel):
    id: int
    name: str


@app.get("/agents", response_model=list[AgentOut])
def list_agents():
    return [
        {"id": 1, "name": "Chat Agent"},
        {"id": 2, "name": "Code Agent"}
    ]
```

这里：

```python
response_model=list[AgentOut]
```

意味着：

> 响应不是一个 AgentOut 对象，而是一个由多个 AgentOut 对象组成的列表。

实际 JSON：

```json
[
  {
    "id": 1,
    "name": "Chat Agent"
  },
  {
    "id": 2,
    "name": "Code Agent"
  }
]
```

### 和单个响应模型有什么区别？

| 声明 | JSON 顶层结构 |
|---|---|
| `response_model=AgentOut` | 对象 `{...}` |
| `response_model=list[AgentOut]` | 数组 `[{...}, {...}]` |

这对未来开发：

```text
GET /agents
GET /chats
GET /tools
```

这样的列表接口很有用。

如果列表中某个元素的字段不符合 `AgentOut`，也可能导致服务器输出验证失败。

## 八、返回任意字典：`response_model=dict[str, float]`

有时，我们并不知道响应会有哪些具体字段。

例如，一个 Agent 执行器返回一些运行指标：

```json
{
  "latency_seconds": 0.25,
  "cost_units": 1.5
}
```

字段名可能随业务变化。

这时不一定要为每个指标创建专门的 Pydantic 模型。

可以写：

```python
@app.get(
    "/metrics",
    response_model=dict[str, float]
)
def get_metrics():
    return {
        "latency_seconds": 0.25,
        "cost_units": 1.5
    }
```

拆开：

```python
dict[str, float]
```

表示：

- 字典的键为字符串。
- 字典的值应该是浮点数。

如果你返回：

```python
{
    "latency_seconds": "invalid"
}
```

由于字符串无法合理转换为浮点数，就可能发生响应验证失败。

### 什么时候用模型，什么时候用字典？

- **结构固定**：建议使用专门的 Pydantic 响应模型。
- **字段名称动态变化**：可以考虑 `dict[str, float]`、`dict[str, int]` 等。

真实 Agent 项目也可以将两者结合，例如在固定的 `AgentResponse` 中加入一个 `metrics: dict[str, float]` 字段。

# 九、第二章综合实战：Agent 创建、列表与不同结果类型 🤖

下面是一个简化、可以直接运行的案例。

```python
from typing import Literal

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()


# ===== 1. Agent 公共字段 =====

class AgentBase(BaseModel):
    name: str
    description: str | None = None


# ===== 2. 创建 Agent 时的输入 =====

class AgentCreate(AgentBase):
    system_prompt: str = Field(min_length=1)


# ===== 3. 对外返回的 Agent 数据 =====

class AgentOut(AgentBase):
    id: int


# ===== 4. 内部存储模型 =====

class AgentInDB(AgentBase):
    id: int
    system_prompt: str
    owner_id: int


# ===== 5. 创建 Agent =====

@app.post("/agents", response_model=AgentOut)
def create_agent(agent: AgentCreate):

    internal = {
        "id": 1,
        **agent.model_dump(),
        "owner_id": 42
    }

    return internal


# ===== 6. 返回 Agent 列表 =====

@app.get("/agents", response_model=list[AgentOut])
def list_agents():

    return [
        {
            "id": 1,
            "name": "Chat Agent",
            "system_prompt": "仅供内部使用"
        },
        {
            "id": 2,
            "name": "Code Agent",
            "description": "帮助用户编写代码"
        }
    ]


# ===== 7. 不同类型的 Agent 结果 =====

class TextResult(BaseModel):
    kind: Literal["text"]
    answer: str


class ToolResult(BaseModel):
    kind: Literal["tool"]
    answer: str
    tools_used: list[str]


@app.get(
    "/results/{kind}",
    response_model=ToolResult | TextResult
)
def read_result(kind: str):

    if kind == "tool":
        return {
            "kind": "tool",
            "answer": "计算完成",
            "tools_used": ["calculator"]
        }

    if kind == "text":
        return {
            "kind": "text",
            "answer": "你好"
        }

    raise HTTPException(
        status_code=404,
        detail="Unknown result kind"
    )
```

### 1. 测试创建 Agent

访问：

```text
POST /agents
```

请求 JSON：

```json
{
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "system_prompt": "你是一个研究助手"
}
```

注意输入模型：

```python
AgentCreate
```

包含 `system_prompt`，因为创建时需要提供它。

但响应模型：

```python
AgentOut
```

没有 `system_prompt`。

所以最终返回：

```json
{
  "name": "Research Agent",
  "description": "负责搜索和整理资料",
  "id": 1
}
```

这里 `system_prompt` 被过滤了。

这只是一个模型教学接口，不会真的把 Agent 写入数据库。将来你需要实现数据库保存、权限管理和运行逻辑。

### 2. 测试 Agent 列表

访问：

```text
GET /agents
```

响应：

```json
[
  {
    "name": "Chat Agent",
    "description": null,
    "id": 1
  },
  {
    "name": "Code Agent",
    "description": "帮助用户编写代码",
    "id": 2
  }
]
```

即使内部字典包含 `system_prompt`，也不会出现在响应中。

### 3. 测试不同类型的结果

访问：

```text
GET /results/text
```

返回：

```json
{
  "kind": "text",
  "answer": "你好"
}
```

访问：

```text
GET /results/tool
```

返回：

```json
{
  "kind": "tool",
  "answer": "计算完成",
  "tools_used": ["calculator"]
}
```

如果访问：

```text
GET /results/unknown
```

因为代码显式抛出了 `HTTPException(404)`，所以返回 404。

### 第二章参考答案

| 题号 | 答案 | 核心原因 |
|---|---|---|
| 1 | B | 输入和输出对敏感字段的需求不同 |
| 2 | C | 数据库不应该存储明文密码 |
| 3 | A | model_dump 返回 Python dict |
| 4 | B | `**` 解包字典 |
| 5 | B | 子类继承父类的字段和验证规则 |
| 6 | C | pass 不新增字段 |
| 7 | B | 联合响应允许多种结构 |
| 8 | C | 返回模型列表 |
| 9 | A | 动态键、浮点数值的字典 |
| 10 | C | 输入和输出使用不同模型 |

**思考题 1：**

```python
class AgentBase(BaseModel):
    name: str
    description: str | None = None


class AgentCreate(AgentBase):
    system_prompt: str


class AgentOut(AgentBase):
    id: int


class AgentInDB(AgentBase):
    id: int
    system_prompt: str
    owner_id: int
```

公共字段统一放在 `AgentBase`，可以减少重复、降低不同模型规则不一致的风险。

**思考题 2：**

```python
AgentOut(
    name="Chat Agent",
    description="聊天助手",
    id=1
)
```

这是字典解包后的等效写法。

**思考题 3：**

```python
class AgentOut(BaseModel):
    name: str
    id: int
```

接口使用：

```python
@app.get("/agents/{agent_id}", response_model=AgentOut)
```

只返回公开字段。内部的 `system_prompt`、`owner_id` 不应该默认向所有调用者暴露；同时仍要根据用户权限决定是否允许访问该 Agent 本身。

## 🎯 今天的学习重点

在继续后面的 FastAPI 章节之前，我最希望你真正掌握三个区别：

**1. 请求验证和响应验证不同。** 客户端输入错误通常是 422，服务端返回的数据不符合响应模型通常是 500。

**2. 一个业务实体不一定只使用一个模型。** `UserIn`、`UserOut`、`UserInDB` 或 `AgentCreate`、`AgentOut`、`AgentInDB` 分别服务于不同环节。

**3. `response_model` 不只是告诉前端 JSON 长什么样，更是控制哪些字段能够对外输出的重要机制。**
