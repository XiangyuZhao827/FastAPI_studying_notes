# 09｜调试（Debugging）

**FastAPI 用户指南 · 独立复习手册｜核心问题：知道 API 出错以后，怎样查出错在哪一行、哪个变量？**

官方文档：https://fastapi.tiangolo.com/zh/tutorial/debugging/

## 一、测试和调试不是一回事

假设你的 Agent 接口应该返回 `{"answer":"你好"}`，实际却得到 `{"answer":""}`。测试能告诉你“结果和预期不符”；但到底是请求 Body 错了、Depends 检查失败、Agent 返回 `None`，还是响应模型处理错了？需要继续追踪。

**调试（Debugging）**就是逐步查看代码执行过程、变量和调用关系，定位问题发生的位置与原因。

| 工具 | 回答的问题 | 示例 |
| --- | --- | --- |
| `/docs` | 这个请求现在返回什么？ | 手动提交 message |
| `pytest + TestClient` | 实际结果是否符合预期？ | 预期 200，实际 500 |
| 调试器 | 为什么会出现这个结果？ | message 实际是空字符串？ |

## 二、断点（Breakpoint）是什么？

所谓“断点”，不是让程序坏掉，而是通知调试器：**运行到这里先暂停**。暂停后可以查看局部变量、调用栈、异常，并决定继续运行还是逐步执行下一行。

例如在 Agent 路由中：

```python
@app.post("/chat")
def chat(request: ChatRequest):
    message = request.message
    answer = run_agent(message)
    return {"answer": answer}
```

你可以在 `answer = run_agent(message)` 处设置断点。请求到来时，程序停在该行，先检查 `message` 是否正确；继续执行后检查 `answer` 是否是预期内容。如果 `message` 正确而 `answer` 为 `None`，就应继续进入 `run_agent()` 查找原因。

## 三、官方关键代码：直接通过 Python 启动 Uvicorn

```python
import uvicorn
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def root():
    a = "a"
    b = "b" + a
    return {"hello world": b}


if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

这是官方教程的最小可运行示例。你以前习惯执行 `fastapi dev main.py`，现在可以让编辑器调试器直接运行 `main.py`，由代码里的 `uvicorn.run(...)` 启动服务。

`port=8000` 表示监听 8000 端口。官方示例用 `host='0.0.0.0'` 监听全部 IPv4 网络接口；如果只是本机学习，建议用 `127.0.0.1`，减少无意对其他设备开放服务的机会。

## 四、`if __name__ == '__main__'` 究竟是什么？

这是 Python 的基础知识，而非 FastAPI 特有功能。它区分两种场景：

**情况 1：你直接执行这个文件**

```bash
python main.py
```

此时 Python 为该文件设置 `__name__ == '__main__'`，条件成立，于是运行 `uvicorn.run(...)`。

**情况 2：测试代码或其他文件导入它**

```python
from main import app
```

这时该模块的 `__name__` 通常是 `main` 而不是 `__main__`，所以不会由于导入就启动服务器。这点对你刚学过的 TestClient 测试特别重要。

**记忆法：**“直接运行才启动；被别人引用则只提供定义。”

## 五、在 VS Code 中怎样做基础调试？

以你之前使用的 Windows `(llm)` Python 环境为例，常见步骤如下：

1. 用 VS Code 打开项目，选择正确的 Python 解释器或虚拟环境。
2. 在路由函数里需要观察的代码行左侧设置断点。
3. 用“运行和调试”启动当前 Python 文件（根据编辑器版本创建 Python 调试配置）。
4. 服务启动后，通过浏览器或 `/docs` 发起请求。
5. 程序执行到断点会暂停；看 VARIABLES、CALL STACK，单步执行或继续运行。

官方还介绍了 PyCharm Debug，原理相同，学习一个编辑器就足够。

**端口提醒：**如果已有另一个 `fastapi dev` 进程占用 8000，调试器再启动一个服务器可能报端口被占用；先停止旧进程。开发重载器也可能让断点停在不符合预期的进程中，初学时直接调试单个程序更直观。

## 六、Agent 实战：按请求流程定位错误

假设用户发送：

```json
{"message":"解释 FastAPI"}
```

但你得到空回答或 500。建议沿着请求链逐层排查：

```text
前端送出 HTTP 请求
  ↓  路由匹配与参数校验（Path / Query / Body）
Depends(get_current_user) 身份与授权
  ↓
路由函数中提取 message、agent_id
  ↓
Agent / LangGraph 业务执行
  ↓
构造 response_model / SSE 事件
  ↓
返回客户端
```

**先看离故障最近的证据：**如果返回 422，优先核对参数格式、字段名称、类型与 Content-Type；401/403 优先检查凭据和资源授权；404 优先检查请求路径、路由顺序与目标资源；500 则查看服务器异常和业务调用情况。

在调用 LLM 的应用中，还可能遇到：SDK 超时、密钥未配置、外部工具失败、模型响应格式变化、流式事件发送中断。这些都需要按具体异常追踪，而不是一概归咎于 FastAPI 框架。

## 七、怎样记录信息才不会泄露用户隐私？

调试过程中可以打印变量，但生产日志不要直接输出：

- 完整的 Bearer Token 或 API Key；
- 用户密码、私密 PDF 正文、完整聊天记录；
- 有权限限制的内部 Agent 配置与敏感文件路径。

可以优先记录请求 ID、状态码、错误类型、时间、脱敏后的业务标识。调试器在本地开发环境操作通常更适合查看敏感变量，生产环境仍要做好访问控制。

## 八、和测试一起建立开发闭环

```text
写一个测试 → 测试失败
    ↓
确认失败的输入与预期
    ↓
设置断点 → 观察请求/依赖/Agent 返回值
    ↓
修复问题 → 再次运行测试
```

这种“测试提出证据、调试定位原因、再次测试确认”的方式，比每次出错都复制粘贴重写全部代码更稳健。

## 九、常见误区

1. **调试器会自动修复错误？** 不会，它帮助你观察和定位错误，修复仍需修改代码。
2. **返回 422 一定是 Agent 模型问题？** 不一定，多数时候先检查 FastAPI 输入验证。
3. **`__name__ == '__main__'` 只属于 FastAPI 吗？** 不是，是 Python 模块运行规则。
4. **按断点后没有暂停，代表程序没有问题？** 不一定。可能请求没到对应路由、调试器没附着到正确进程等。
5. **测试通过就无需调试？** 自动测试覆盖有限；当预期与实际不一致时仍可使用调试器排查。

## 十、5 道复习题（附答案解析）

**1. 测试与调试最核心的分工是什么？**  答：测试判断行为是否符合预期；调试定位不符合预期的具体原因。

**2. 断点能让程序怎样运行？**  答：执行到指定行时暂停，方便观察变量、调用栈和逐步执行。

**3. 直接运行 `python main.py` 与 `from main import app` 对 __name__ 有什么影响？**  答：前者使该模块 __name__ 为 __main__；后者通常为模块名 main。

**4. 为什么调试时经常要停止原来的 fastapi dev 服务？**  答：避免两台服务器争用同一端口，也减少多进程带来的断点定位混乱。

**5. 用户输入合法但 Agent 回复为空，应优先观察什么？**  答：进入路由后的 message，调用 Agent 前的入参，以及调用后的返回值，再逐层定位。

## 十一、思考题

你正在排查“alice 成功登录，但访问自己的 Agent 经常返回 403”。你会在哪些地方设置断点？怎样避免通过日志泄露 Token？

**参考方向：**观察已验证用户、agent_id、服务端资源 owner 和授权条件；避免打印完整 Authorization Header、JWT 或密码，只记录脱敏标识与错误类别。

**本章一句话总结：**测试告诉你结果不对；调试器让你逐行观察请求怎样进入 Agent、错误从哪里出现。
